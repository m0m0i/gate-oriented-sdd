# Spec: the Claude Code gates ship from the plugin
- Slug: 256-the-claude-code-gates-ship-from-the-plugin   Issue: 256   Type: feature   Status: approved
- Author: m0m0i   Date: 2026-10-07

## 1. Requirements (WHAT / WHY)

- User story: As a developer whose project ran `init` on Claude Code, I want a fix to a gate to reach my project by plugin update, so that the gate I am relying on is the one that was last fixed, with no pull request in my repository per fix.

- Serves: CAP-5, fixes that reach the people running it (LV-5). Today the skills follow the plugin and the gates do not: `init` copies four scripts into `.claude/hooks/` and nothing refreshes them. #245 measured four consumer repositories at 90 to 359 lines behind the plugin's `review-gate.sh`, backlog row 1 re-measured them at 130 to 377, and #254 (0.22.1) is one more fix that reaches a project only by re-copying. The Claude Code path changes; the Antigravity path does not, because a plugin-shipped hook runs there with the plugin directory as cwd (`hooks/templates/README.md`).

- What is already known, measured 2026-10-06 in scratch directories on Claude Code 2.1.290 and the Antigravity CLI 1.2.16, and recorded in `docs/verified.md` by this spec (AC9):
  - **V1 holds.** A plugin-shipped `Stop` hook and `SessionStart` hook, declared at `.claude-plugin/hooks.json` through the manifest's `"hooks"` field, both ran with the project as cwd and `CLAUDE_PLUGIN_ROOT` set to the plugin directory.
  - **V2 answered.** With `Stop` defined by the plugin and by the project's `.claude/settings.json`, both commands ran, once each. A stand-down guard is therefore what prevents a double gate, not the harness.
  - **V5 answered at the validator level.** `agy plugin validate` reports `hooks : skipped (not found)` with the file and the manifest field in place, and `hooks : 1 processed` with a root `hooks.json`. The runtime loader log was not read.
  - **V3 answered for the case that matters, 2026-10-07**, against the maintainer's user-scope install, which holds `gate-sdd@gate-oriented-sdd` from an unpinned `gate-oriented-sdd` marketplace with `autoUpdate: true`. A scratch project declared the same marketplace name pinned to `#gate-sdd--v0.21.5` and enabled the plugin. A session there loaded the cached 0.22.0 (`Attempting to load skills from plugin gate-sdd default skillsPath: …/cache/gate-oriented-sdd/gate-sdd/0.22.0/skills`), the shared marketplace clone stayed at `ab518af`, no new cache directory appeared, `known_marketplaces.json` was unchanged, and `installed_plugins.json` gained a project-scope entry at the existing 0.22.0 path. `claude plugin install gate-sdd@gate-oriented-sdd --scope project` inside that project answered "already installed (scope: project)" and moved nothing. So a project-scope pin under a marketplace name the user scope already knows is ignored, and it cannot move the shared clone. The other branch, a machine where only the project declares the marketplace, was not run.
  - **V4 answered as far as it can be produced.** Every scope entry for one plugin id pointed at one cache path, and the session loaded that path. Two versions cached for one id did not arise, because the pin that would have produced them was ignored.

- Acceptance criteria:
  - [ ] **AC1:** WHEN the plugin is installed on Claude Code and the project has `.steering/` THE SYSTEM SHALL run the quality gate and the review gate on `Stop`, and the steering digest on `SessionStart`, from `${CLAUDE_PLUGIN_ROOT}/hooks/`, with no gate script in the project.
  - [ ] **AC2:** WHEN the plugin is enabled and the project has no `.steering/` THE plugin's hooks SHALL exit 0 with no output, so a user-scope install is silent in projects that do not use the harness.
  - [ ] **AC3:** WHEN the project's `.claude/settings.json` holds a `Stop` or `SessionStart` entry that runs a project copy of the same gate THE plugin's hook for that event SHALL stand down, so the gate runs once per turn; WHEN the project holds the copied file and no such entry THE plugin's hook SHALL run. Presence of the file alone is not evidence that it runs (backlog row 1, under `- Owns: gates never fail open`).
  - [ ] **AC4:** WHEN `init` runs on Claude Code against a new project THE SYSTEM SHALL write `extraKnownMarketplaces` with `"autoUpdate": true` and no `#ref`, and `enabledPlugins`, into the project's committed `.claude/settings.json`, keep the per-language `PostToolUse` fast check there, and SHALL NOT copy `quality-gate.sh`, `review-gate.sh` or `steering-digest.sh`.
  - [ ] **AC5:** WHEN `init` runs on Claude Code against a project with legacy copies THE SYSTEM SHALL remove the gate scripts and their `Stop` and `SessionStart` entries, keep the `PostToolUse` entry, write the declaration of AC4, and leave `assets/check-steering-anchors.sh` and `assets/check-unreviewed-work.sh` green in that project, both of which look for `gate-lib.sh` under the project's hooks directory. Whether `gate-lib.sh` stays copied or the two checks learn a second location is Q1.
  - [ ] **AC6:** WHEN the plugin directory is installed on Antigravity THE SYSTEM SHALL load no Claude Code hooks file, and `init` on Antigravity SHALL install `.agents/hooks.json` and `.agents/hooks/` exactly as before.
  - [ ] **AC7:** every gate keeps both blocking channels, JSON for Antigravity and exit 2 for Claude Code, and `scripts/test-gates.sh` keeps its verdicts.
  - [ ] **AC8:** `scripts/test-gates.sh` covers AC2 and AC3 with cases that run the plugin's hook commands as the hooks file states them; `scripts/check-manifests.py` fails if `hooks/hooks.json` or a root `hooks.json` appears, if the manifest's `"hooks"` field and the file it names disagree, or if the Claude Code hooks file and `hooks/templates/antigravity.hooks.json` disagree on which gates they cover, the pairing it already checks between the two templates.
  - [ ] **AC9:** `docs/verified.md` records V1 to V5 with versions and exact observations, including a V3 or V4 that did not run or fell the unsafe way; `hooks/templates/README.md` says the Claude Code template no longer carries the gates and why; `docs/fidelity.md`'s working-directory paragraph and table say how gates are delivered per harness.
  - [ ] **AC10:** the Design says why gates ship from the plugin where ADR-7 took the reviewers into what `init` copies, and a decision record holds it.
  - [ ] **AC11:** every new case in `scripts/test-gates.sh` fails against `ab518af`'s `hooks/` and `scripts/` for the stated reason and passes after, except pins, which pass before and after and say so.

- Out of scope:
  - `README.md`, `README.ja.md` and `docs/layout.md`: #257.
  - Antigravity plugin-shipped hooks; the `PostToolUse` fast check; the per-project reviewers and the shared contract's drift (#245 names it for its own issue); a version floor in `.steering/tech.md`.
  - A tag on every release so a pin can target any version: #68, row 13.
  - A consumer's CI copy of the validator loop, and its copy of `check-unreviewed-work.sh`, which reads the project's library either way (Q1).

### Clarifications

Asked and answered 2026-10-07.

- **Q1. Once the gates ship from the plugin, where do a project's own checks find `gate-lib.sh`? `assets/check-steering-anchors.sh` is on every project's `- Validators:` line and `assets/check-unreviewed-work.sh` runs in its CI, and both look under the project's hooks directory.** Discover by environment. The two checks look in `$GATE_SDD_HOOKS` first, then the three directories they look in today, then `$CLAUDE_PLUGIN_ROOT/hooks`. At turn end the plugin's gate runs the validators with `CLAUDE_PLUGIN_ROOT` in their environment, so the anchor check reads the plugin's own library; in CI `init` has the workflow check the plugin out and set `GATE_SDD_HOOKS`; by hand, a project with no copy sets the variable or gets the existing "cannot find gate-lib.sh" error, which now names it. `init` stops copying `gate-lib.sh` as well, so nothing in a Claude Code project drifts, and CI follows the plugin too. Rejected: keeping the library copied, which leaves CI's unreviewed-work check running yesterday's fail-open fixes; and copying it with a lag report in the digest, which is one more thing the digest does for a copy that should not exist. → AC5, Design.
- **Not asked, because the measurements or the repo answer them:** the hooks file lives at `.claude-plugin/hooks.json`, which V1 showed Claude Code loads through the manifest's `"hooks"` field and V5 showed Antigravity's validator does not see. The stand-down evidence is the project's settings naming the gate's file under the gate's event (Design), because V2 showed the harness runs both otherwise. The version bump is a minor, 0.23.0: `init`'s install path and what a project commits both change, like #146. This repository keeps running its hooks from source (ADR-6); its `.claude/settings.json` is the stand-down evidence, so the plugin's gates are silent here and the dogfood instance is unchanged.

## 2. Design (HOW)

- **Approach and key decisions.**
  1. **A wrapper, not three guarded one-liners.** `hooks/plugin-gate.sh <gate>` is what `.claude-plugin/hooks.json` runs: `sh "${CLAUDE_PLUGIN_ROOT}/hooks/plugin-gate.sh" quality-gate.sh` on `Stop`, the same for `review-gate.sh`, and `steering-digest.sh` on `SessionStart` with the template's matcher. The wrapper exits 0 silently when `.steering/` is absent (AC2). It stands down, exit 0 and silent, when the project's `.claude/settings.json` or `.claude/settings.local.json` names the gate's filename and declares the gate's event, `Stop` for the gates and `SessionStart` for the digest (AC3). Otherwise it `exec`s `sh "$DIR/<gate>"`, so the gate runs with the project as cwd and the plugin's own library beside it. A gate file missing from the plugin blocks with the bootstrap guard's shape and a re-install remedy: a broken install is loud, not silent. The guard lives in a script because a guard in a JSON string is one nobody tests.
  2. **Stand-down evidence is text, read with `grep`, and biased toward running.** A POSIX hook cannot parse JSON by event, and the two wrong directions are not symmetric: both gates running costs a second validator pass, neither running is a fail-open. So the plugin stands down only when the file names the gate *and* the event; a file that names the gate under another event, or an entry that was deleted while the copy stayed on disk, runs the plugin's gate. The copied file alone is never evidence.
  3. **Library discovery, per Q1.** Both `assets/` checks: `$GATE_SDD_HOOKS`, then `hooks`, `.claude/hooks`, `.agents/hooks`, then `$CLAUDE_PLUGIN_ROOT/hooks`. The explicit variable wins so CI and a by-hand run can say where the library is; the three directories keep this repository on its source and an un-migrated project on its copy; the plugin root is last so that a dogfood turn in this repository never reads an installed copy. The error names all five.
  4. **`init` on Claude Code writes a declaration, not scripts.** The rendered `.claude/settings.json` holds the `PostToolUse` fast check, `extraKnownMarketplaces` with `"autoUpdate": true` and no `#ref` (V3: a pin under a known name is ignored anyway, which #257 says in prose), and `enabledPlugins`. Migration removes `quality-gate.sh`, `review-gate.sh`, `steering-digest.sh` and `gate-lib.sh` from `.claude/hooks/` and their `Stop` and `SessionStart` entries, keeps `PostToolUse`, and the CI step that runs `check-unreviewed-work.sh` checks the plugin out at a ref and exports `GATE_SDD_HOOKS`. On Antigravity, and for the Antigravity half of a dual-target project, nothing changes: the five scripts are copied into `.agents/hooks/`, and the checks find the library there.
  5. **Why gates ship from the plugin where ADR-7 took the reviewers the other way.** A reviewer is adapted and pinned per project, so the project owns its text and the lock exists to keep a plugin update from changing it (ADR-2). A gate is the opposite: identical in every project, configured through `.steering/tech.md`, and most dangerous when stale. The two layers ship differently because one is the project's and one is the plugin's. ADR-8 records it.
  6. **The guards.** `scripts/check-manifests.py` fails if `hooks/hooks.json` or a root `hooks.json` exists, if the manifest's `"hooks"` field does not name a readable JSON object, if any command in that file names a script that does not exist under `hooks/`, and if the union of the plugin file's events and the Claude Code template's events does not pair with the Antigravity template's as the two templates pair today. `scripts/check-version-bump.py`'s `SHIPPED` and `scripts/package-release.py` carry `.claude-plugin/hooks.json`, and `.steering/tech.md`'s `- Source globs:` names it, so a change to it re-stales a receipt.
- **Affected files:** `hooks/plugin-gate.sh` (new), `.claude-plugin/hooks.json` (new), `.claude-plugin/plugin.json`, `hooks/templates/claude-code.settings.json`, `hooks/templates/README.md`, `assets/check-steering-anchors.sh`, `assets/check-unreviewed-work.sh`, `skills/init/SKILL.md`, `scripts/check-manifests.py`, `scripts/check-skill-contracts.py`, `scripts/check-version-bump.py`, `scripts/package-release.py`, `scripts/test-gates.sh`, `.steering/tech.md`, `AGENTS.md`, `docs/fidelity.md`, `docs/verified.md`, `docs/decisions/ADR-8-the-claude-code-gates-ship-from-the-plugin.md`.
- **Contract changes, and who consumes them:** a Claude Code project's committed `.claude/settings.json` gains two keys and loses two hook events; its CI gains a checkout and a variable; `GATE_SDD_HOOKS` is a new name both `assets/` checks read. Antigravity projects see no change. `claude plugin validate . --strict` runs in CI on the manifest with its new field.
- **Risks and trade-offs:**
  - **A project that cannot be migrated yet keeps its copies and the plugin stands down**, which is today's behaviour, drift included. That is the trade for never running a gate twice, and the migration is one `init` run.
  - **Stand-down by text.** A settings file that names `review-gate.sh` under `Stop` without running it is the one shape that silences both. It is contrived, and the alternative is parsing JSON in `sh`.
  - **`CLAUDE_PLUGIN_ROOT` reaches validators only from the plugin's gate.** A by-hand `./scripts/check-steering-anchors.sh` in a migrated project needs `GATE_SDD_HOOKS`; the error says so.
  - **Timeouts.** The wrapper adds a process; the template's 180, 30 and 15 seconds carry over unchanged.
  - **Validation.** `claude plugin validate --strict` takes minutes here; CI's job is the record, as for #235.
