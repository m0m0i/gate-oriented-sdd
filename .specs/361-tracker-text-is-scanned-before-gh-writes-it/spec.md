# Spec: tracker text an agent session writes with gh is scanned before the command runs
- Slug: 361-tracker-text-is-scanned-before-gh-writes-it   Issue: 361   Type: feature   Status: approved
- Author: m0m0i   Date: 2026-11-15

## 1. Requirements (WHAT / WHY)
- User story: As the maintainer of a public repository extracted from private work, I want a `gh` command that would publish a private word stopped before it runs, in whichever project my agent session is working, so that the tracker stays as clean as the history #360 protects.
- Serves: M-1 in `docs/CONTRACT.md` and `- Owns: gates never fail open`. No capability in `docs/PRD.md`.
- Why nothing stops it today, on the maintainer's machine on 2026-11-15 (Claude Code 2.1.325, gh 2.104.0):
  - `~/.claude/settings.json` has no `hooks` key, and its `permissions.allow` holds `Bash(gh *)`, so every `gh` write runs without a prompt (measured).
  - #360's hooks see what `git` publishes. A title, a body, a comment, release notes, a merge message and a release's tag are written on the server and pass none of them. CI scans a pull request's title and body only after they are public, and only in this repository.
  - The maintainer's past sessions held 372 Bash commands with a `gh` write, by a quote- and heredoc-aware lexer over the transcripts; 196 of them ran in another project's directory (measured). A check that only this repository's `.claude/settings.json` registers misses those.
- What the criteria rest on:
  - **A `PreToolUse` command hook fails open by default** (measured, headless sessions): exit 1, a kill by signal, a timeout, a missing script and invalid JSON all let the Bash call run. With `"onFailure": "block"` (2.1.295 or later) each of those blocks, except stdout that begins with `{` and is not JSON at exit 0, which 2.1.325 reads as plain text and lets through (measured; the documentation says otherwise). Exit 2 blocks, in `bypassPermissions` mode too (measured).
  - **`if: "Bash(gh *)"` is not a filter to rely on:** it did not fire for `gh` called by an absolute path (measured).
  - **A project can switch a user-level hook off** with `"disableAllHooks": true` in its `.claude/settings.json` (measured for a hook from `--settings`, which outranks project settings). `--bare`, `--safe-mode`, `--setting-sources` without `user`, and a `tool.check` mod on an account without managed settings pass a hook too (documented).
  - **A project's `env` setting reaches the hook's process** (measured): `PYTHONPATH`, `DEVELOPER_DIR`, `GH_REPO` and `GATE_SDD_LEAKAGE_PATTERNS` arrived; `HOME`, `XDG_CONFIG_HOME` and `XDG_DATA_HOME` were dropped. A `PYTHONPATH` holding a module named like a standard one made a Python hook exit 0 before its first line ran.
  - **The Bash tool runs zsh** (measured: `/bin/zsh -c`, zsh 5.9, after sourcing Claude Code's shell snapshot), so zsh decides which words `gh` receives.
  - **The command string is not the text** (measured, synthetic pattern): `--body "Zq_Ex""act"`, `$'Zq_\x45xact'`, `Zq_\Exact` and `Zq_E{x..x}act` were clean when the raw string was scanned, and `gh` received the word. 261 past writes took their body from a file; 68 of those files were written in the same command, after the hook would run, and 14 came from a generator such as `gh issue view … > f`, which no hook can read ahead of time.
  - **`gh` takes its target from more than `-R`** (measured against a local fake server): `remote.<name>.gh-resolved`, which `gh repo set-default` writes, overrides the remotes; an issue or pull-request URL given as an argument overrides `GH_REPO`; `repo edit <owner>/<repo>` and `repo create <owner>/<name>` name their own target; an ssh host alias or an `insteadOf` rewrite hides `github.com` from a remote's URL.
  - **The public tier would block legitimate writes elsewhere:** it hit 28 of 306 past `gh` writes from directories that are not this repository's clones, none of them naming this repository (measured, a regex over the transcripts).
- Acceptance criteria:
  - [ ] **AC1:** WHEN a Claude Code session on the maintainer's machine, in any project, runs a `gh` command through the Bash tool or the Monitor tool, or through the desktop app's terminal tool where `PreToolUse` fires for it, and the command sends text to a guarded target (AC6) that matches a failing pattern THE SYSTEM SHALL block it before it runs. The text is every value the command sends — its arguments, the content of every file and of the standard input it reads, and the names and labels of files it publishes. The block names where the text came from (a flag, a file, standard input) and the line. The hook's output never holds the matched text or a pattern.
  - [ ] **AC2:** WHEN the text is not in the command line itself (a body, notes or input file, `-F key=@file`, an attachment, a gist's files, a release's assets, a heredoc, a here-string or a redirect on standard input) THE SYSTEM SHALL read it from where `gh` would. A file the same command writes with a heredoc or a literal `printf` or `echo` before `gh` reads it is read from that text.
  - [ ] **AC3:** WHEN the hook cannot recover the text `gh` would send (`--fill` in any form, `--editor`, `--web`, `--recover`, `--template`, `--notes-from-tag`, `--generate-notes`, a variable or substitution it cannot resolve, a brace or glob expansion, a pipe, a file missing or rewritten earlier in the command, a flag its table does not list) or cannot tell what a command runs, cannot load the private patterns or the exempt list, crashes, or times out THE SYSTEM SHALL block, and SHALL NOT let the command run unscanned.
  - [ ] **AC4:** WHEN a command does not hold the word `gh` THE SYSTEM SHALL let it run without loading the patterns, so that a fault in the pattern file or the exempt list blocks only a command that mentions `gh`. A hook that cannot start blocks every Bash call, and the block names the cause.
  - [ ] **AC5:** WHEN this repository's working-tree guard runs on a machine with a Claude Code configuration whose settings do not register the hook as the installer prints it, register an installed copy older than the default branch's, or switch hooks off THE SYSTEM SHALL exit 1 and name the install command, as #360's check does for absent git hooks. The check runs the registered command on a probe and fails unless it passes a command without `gh` and blocks a synthetic hit. `--no-hook-check` exempts the run; a machine with no Claude Code configuration skips it and says so on the clean line.
  - [ ] **AC6:** every target is guarded except a repository named in an exempt list beside the pattern file, by `<owner>/<repo>` or `<owner>/*` with a stated reason. A write is exempt only when every repository it could reach is: the one `-R`/`--repo`, a `GH_REPO` assignment on the invocation, a URL or repository argument, or an `api` endpoint names; otherwise each remote of the directory it runs in, each `gh-resolved` value, and `GH_REPO` from the environment. A write with no repository (a gist, GraphQL, an owner-level path) and a target the hook cannot resolve are guarded. An absent list exempts nothing.
  - [ ] **AC7:** the repository holds the hook, its install command, its cases in `scripts/test-gates.sh` built on synthetic patterns only, and the instructions for registering it. It does not edit the maintainer's user-level settings. The hook's interpreter and every process it starts run with an environment the hook builds, so a project's `env` setting changes neither what it runs nor which patterns it loads.
  - [ ] **AC8:** each block reason, each fault and each check of AC5 has a case that asserts its own sentence, shown red by removing that one check.
  - [ ] **AC9:** a Bash call with no `gh` word takes under 100 ms more with the hook than without it, and a `gh` write under 1 s more; and the hook, replayed over the maintainer's past Bash commands, blocks none that sent no private text, apart from blocks counted by reason and each accepted in ADR-13. Measured on the maintainer's machine and recorded; not suite cases.
  - [ ] **AC10:** `CONTRIBUTING.md` says what the hook scans, how to install and register it and write the exempt list, and what passes it: a project's `disableAllHooks`, `--bare`, `--safe-mode`, a session without user settings, a mod's approval, another hook that rewrites the command, a shell alias or function from the user's startup files, a script file run by name, an HTTP client other than `gh`, and the GitHub web UI. ADR-13 records why a harness tool hook, which ADR-12 declined for `git`, is the one place `gh` can be checked, and why rules G-3 and G-5 of this repository's reviewer do not apply to it. M-1's row in `docs/CONTRACT.md` names it, and `docs/verified.md` and `docs/fidelity.md` record what was measured.
  - [ ] **AC11:** nothing here is shipped: the change is under `scripts/`, `.steering/`, `docs/` and `CONTRIBUTING.md`, with no version bump. `AGENTS.md` is not touched.
- Out of scope:
  - **Commits, pushes and ref names:** #360.
  - **Antigravity.** The issue's criterion is a Claude Code session; whether Antigravity's `PreToolUse` can deny a shell command is measured by #365.
  - **Cloud sessions,** which read no user-level settings.
  - **GitHub MCP tools.** None is configured on the maintainer's machine (measured 2026-11-15). Adding one needs its tool names in the matcher, by a later issue.
  - **Text written through the GitHub web UI,** or typed into github.com by a browser tool.
  - **An adversarial agent.** The hook stops a private word written by mistake. The switches AC10 lists turn it off, and only managed settings, which need administrator rights, could close them. A command spelt to hide `gh` from a reader (`$'\x67h'`) is in the same class.

### Clarifications
Asked and answered 2026-11-15.

1. **Which writes are scanned, when the hook runs in every project?** All but those to an exempt list (AC6). A guarded list was declined: a new public repository would be unguarded until added.
2. **Which of a write's text is scanned?** All of it (AC1), the merge message and the release tag that the issue left open included.
3. **Is a broken install allowed to block every Bash call?** Yes (AC4). An `if` filter was declined because it missed `gh` called by an absolute path.
4. **Where is an unregistered hook reported?** This repository's working-tree guard fails (AC5). A check every project ran would be switched off by the same `disableAllHooks` that switches off the hook.

## 2. Design (HOW)
Every claim below marked measured was run on the maintainer's machine on 2026-11-15, on Claude Code 2.1.325 and gh 2.104.0, by this spec's four scouts and four critics, with synthetic patterns only. "The table" is the per-subcommand table the hook carries.

- Approach and key decisions:
  - **Registration.** `PreToolUse`, `"matcher": "Bash|mcp__terminal__run_in_terminal"`, one command handler in exec form — `"command": <an interpreter's absolute path>, "args": ["-I", <snapshot>/gh_guard.py]` — with `"onFailure": "block"`, `"timeout": 30`, no `if` and no `async`. Measured: exec form runs on 2.1.325; the matcher is an exact list; it fires for Bash and for the Monitor tool, whose block holds. `-I` keeps `PYTHONPATH`, `PYTHONHOME`, the user site and the script's own directory off `sys.path` (measured: without it a project's `PYTHONPATH` made the hook exit 0 before it ran).
  - **The interpreter** is resolved once by the installer and named by its real path: on macOS `/usr/bin/xcrun -f python3` followed to its file, because `/usr/bin/python3` is a shim that a project's `DEVELOPER_DIR` reroutes and that fails while an Xcode licence is unaccepted (measured); elsewhere `python3`'s real path. It must be 3.9 or later, and the hook uses no syntax or library newer than 3.9. A version manager's shim is refused.
  - **The protocol.** Exit 2 with a reason on stderr blocks; exit 0 with nothing on stdout passes; exit 0 with one well-formed `{"systemMessage": …}` passes with a warning, which reaches the user and not the model and grants no permission (measured). The hook never prints a decision as JSON: a deny cut short would read as plain text and pass. The module returns its decision and never exits; a top-level handler in the entry script turns every exception, `SystemExit` with any code included, and a returned code other than 0 or 2, into exit 2, and prints the exception's type, never its message, which can hold a value. Anything the module prints to stdout is discarded, so only the entry script writes it.
  - **The block's wording.** `gate-sdd gh guard: blocked. LEAK [fail] in the --body-file text (<path>), line 3. The matched text is withheld.` A fault: `gate-sdd gh guard: blocked. Cannot recover the text gh would send: --fill.` Each ends with what to do: rewrite the text, write it to a file the hook can read, or exempt the repository with a reason.
  - **A small entry script imports the module.** `gh_guard.py` adds its own directory to `sys.path` and imports `gh_guard_lib`, which the installer compiles, because the 3.9 interpreter recompiles a 2,400-line script on every run (72 ms measured, against 45 ms for a stub).
  - **The fast path.** The command passes, with no file read and no pattern loaded, unless it holds `gh` at a word boundary once quotes and backslashes are removed. For the terminal tool the command is `tool_input.command`.
  - **The slow path parses the command as zsh** runs it in the Bash tool: words with `'…'`, `"…"`, `$'…'` and backslash quoting rebuilt; `&&`, `||`, `;`, `|`, `&` and newlines; `(…)` and `{ …; }`; redirections, including `<<`, `<<-` and `<<<`; `$(…)` and backticks, nested; a leading `~` and `=word` expanded. An unquoted brace (`{a,b}`, `{a..b}`), glob character or zsh parameter flag inside a value a write sends, or a path it reads, is unrecoverable. A construct the lexer does not handle — `case`, a function definition, `eval`, arithmetic, an unterminated quote — passes only if no `gh` word lies inside it.
  - **Every `gh` word must be explained, or the command blocks.** A `gh` word is explained when it is: the command word of a `gh` invocation; an argument of a command that never runs its arguments (`echo`, `printf`, `which`, `type`, `whence`, `man`, `grep`, `rg`, `cat`, `ls`, and `git` other than `git -c` and `git config`); a value a `gh` invocation sends; or text in a heredoc read by `cat` or `tee` into a file the command does not then run. An invocation's command word is a word whose rebuilt value is `gh` or ends in `/gh`, after leading assignments and the wrappers `env`, `command`, `exec`, `builtin`, `noglob`, `nocorrect`, `time`, `nohup`, `nice`, `caffeinate` and `timeout`, each with its options. `G=gh; $G` is resolved through the tracked assignment. `sh -c`, `bash -c` and `zsh -c` with a literal script, a heredoc given to one of them, and a file the same command writes with a heredoc and then runs with one of them or by its path, are parsed again. Anything else holding a `gh` word blocks: measured, `nice gh`, `caffeinate -i gh`, `${:-gh}`, `$(echo gh)`, `"${commands[gh]}"` and `builtin exec gh` each reached `gh`. `alias`, `hash` or a function defined in the command, `xargs`, and inline code for `python`, `node`, `perl` or `ruby` are among them.
  - **Classification.** The subcommand path is read after the global flags that may precede it, with every flag that classifies or targets taking its last occurrence before `--`, and `--help` meaning help only when true (measured: `--help=false` ran the write). The table lists each path of gh 2.104.0 from `gh help reference` (236 paths) with its built-in aliases (`issue new`, `pr ls`, `co`, and the rest), as read, write, local state or arbitrary execution. A read passes. `api` is a read only when its last method flag is `GET`, compared without case, or when it has no method flag and no `-f`, `-F` or `--input`; and `api graphql` only when its query text is recoverable and holds no `mutation`. Arbitrary execution — `copilot`, `extension exec`, `install` and `upgrade`, `codespace ssh`, `cp`, `code`, `jupyter` and `ports forward`, and any top-level word that is not a built-in command or alias, which covers gh aliases and extensions — blocks whatever the target. Local state (`alias set`, `config set`, `repo set-default`, `auth …`) passes alone and makes a later write in the same command's target unresolvable. Aliases are not resolved: their definitions are YAML, which the standard library cannot read, and one defined in the same command is invisible to a lookup made before it runs (measured).
  - **What a write sends is every value after the subcommand path**, flags and positionals alike, except a path given to a flag that names a file, whose content is read instead. A published file's name and its `#label` are values too. The table gives each path's flags from `gh <path> --help` on 2.104.0, with short and long forms, whether each takes a value, and whether it names a file, reads standard input or makes the text unrecoverable; it parses `-bX`, `--body=X`, `-b=X` and combined short flags (measured). A flag the table lacks for that path blocks. `-f key=@file` on `api` is literal text; `-F key=@file` reads the file and `-F key=@-` standard input (measured). `{owner}`, `{repo}` and `{branch}` in a `-F` value expand as `gh` expands them, and are unrecoverable when more than one repository is a candidate. When `gh --version` differs from the table's in major or minor, a write passes with a `systemMessage` saying the table may be out of date.
  - **Text not on the command line.** A file is read at hook time, relative to the directory the command has reached; for the terminal tool that starts at `tool_input.cwd`. Standard input is the heredoc, here-string or file redirected into the invocation, scanned for every write whatever its flags (measured: `variable set`, `workflow run --json` and `gist create` with no file read it); a pipe into a write is unrecoverable. `/dev/stdin`, `/dev/fd/*` and `/proc/*/fd/*` are standard input; any other path under `/dev` but `/dev/null`, and a file that is not a regular file, is unrecoverable. A file the same command writes before `gh` reads it is taken from a heredoc or a literal `printf` or `echo` into it, appended to its current content under `>>`; a file the command names anywhere else first — an `mv`, a `sed -i`, the output of `gh issue view > f` — is unrecoverable, as is a missing file. Attachments, gist files and release assets are scanned as their bytes, and one over 50 MB blocks with that cause, so that a timeout is always a fault; an archive is not opened.
  - **Variables and directories.** Literal assignments earlier in the same command (`D=/x`, `export D=/x`) are tracked in order; `$D`, `${D}` and `$HOME` expand. `cd <literal>` moves the directory later commands of the same list run in; a subshell's `cd` stays in it. Any other expansion in a value a write sends, or in a path it reads, is unrecoverable.
  - **Each source is scanned on its own** by the guard beside the hook, `sh check-leakage.sh --text`, with each carriage return before a line end, and each alone, made a line end, as CI does: a `$`-anchored expression misses a line that ends in `\r\n` (measured). The guard's stdout is discarded, and its stderr is read only for `LEAK` and `WARNING` lines; anything else it prints is a fault. Any non-zero exit blocks, a hit and a fault alike.
  - **Every process the hook starts gets an environment built from nothing:** `PATH=/usr/bin:/bin`, `HOME` and `XDG_CONFIG_HOME` as the hook resolved them, and a UTF-8 locale. Nothing else from the hook's environment reaches the guard or `git`, so `GATE_SDD_LEAKAGE_PATTERNS`, which a project's `env` delivers (measured), and any knob a later guard gains, stay out.
  - **The patterns are the guard's,** at `${XDG_CONFIG_HOME:-$HOME/.config}/gate-sdd/leakage-patterns`. Projects cannot set `HOME` or `XDG_*` (measured), and the suite redirects through them.
  - **The exempt list** is `${XDG_CONFIG_HOME:-$HOME/.config}/gate-sdd/leakage-exempt-repositories`: one `<owner>/<repo>` or `<owner>/*` per line, followed by a reason, `#` comments and blank lines ignored, compared without case. A line without a reason, or of any other shape, is a fault, and a fault blocks every `gh` write.
  - **The target.** An invocation that names its repository decides alone: `-R`/`--repo` (`OWNER/REPO`, `HOST/OWNER/REPO`, an https or scp-style URL, `.git` stripped only from a URL, as `gh` does — measured), a `GH_REPO` assignment on the invocation, an issue or pull-request URL argument, a `repo` subcommand's repository argument, or an `api` endpoint `repos/<owner>/<repo>/…`, with one leading `/` stripped and a full URL on `api.github.com` or `uploads.github.com` read the same way. Otherwise the candidates are every remote of the directory the command has reached, by the owner and repository in the path of `git remote get-url --all` and of each push URL, whatever the host (an ssh alias or an `insteadOf` rewrite then still yields the repository); every `remote.*.gh-resolved` value of that form; and `GH_REPO` from the hook's environment. The write is exempt only if every candidate is. Guarded without candidates: a URL path that does not parse; an endpoint holding `..`, `%2e`, `%2f`, `//` or a backslash; `--hostname` other than `github.com`; a gist; GraphQL; an owner-level path (`--owner`, `--org`, `repo create` without an owner); `env -i`, `env -u`, `unset`, or an assignment of `GIT_*`, `GH_CONFIG_DIR` or `GH_HOST` before the write; and a `git remote`, `git config`, `gh repo set-default` or `gh config set` earlier in the command.
  - **The installer, `scripts/install-gh-hook.sh`,** writes `gh_guard.py`, `gh_guard_lib.py` (compiled) and `check-leakage.sh` into a new versioned directory under `${XDG_DATA_HOME:-$HOME/.local/share}/gate-sdd/gh-hook/`, then points the `current` link at it in one rename, so no Bash call ever finds the hook half-installed; a failed install leaves the old version running. It refuses an older version than the one installed, and an interpreter it cannot resolve. It prints the entry to add, with absolute paths through `current`, and says whether `~/.claude/settings.json` already holds it. It never writes that file (AC7). A snapshot, because an entry naming a checkout would run whatever branch or uncommitted edit that checkout holds.
  - **The registration check** runs in `check-leakage.sh`'s working-tree mode, inside a git repository, after the git hooks' check and under the same `--no-hook-check`, as the reference copy of `gh_guard.py --check-registration` run by `python3 -I`. Its reference is the default branch's `scripts/claude-hooks/`, read with `git show`, so a branch that edits the hook does not have to install its work in progress for every session on the machine; where the default branch has none, the worktree's copy is the reference. It skips, and says so on the clean line, when neither `$CLAUDE_CONFIG_DIR` nor `~/.claude` exists. Otherwise it fails, with one sentence per fault, when: a settings file is unreadable or not JSON; no `PreToolUse` entry in user or managed settings covers `Bash` and the terminal tool with a handler in exec form naming a resolved interpreter, `-I` and the installed `gh_guard.py`; that handler has an `if`, is async, or lacks `"onFailure": "block"`; the installed version line is lower than the reference's, or equal with any installed file's bytes different; `disableAllHooks` is true in user or managed settings or in this repository's `.claude/settings.json` or `.claude/settings.local.json`, or managed settings set `allowManagedHooksOnly`; a Claude Code shell snapshot defines an alias or a function whose body holds a `gh` word; or the registered command, run exactly as registered with a scratch `HOME` holding a synthetic pattern, does not pass a command without `gh` with empty stdout and block `gh issue create --body <the synthetic word>` without the word in its output.
  - **Why G-3 and G-5 do not apply** (`.claude/agents/gate-sdd-reviewer/rules/gates-and-guards.md`). G-3 asks a blocking gate to speak both harnesses' channels; this hook is registered in Claude Code alone, and JSON on stdout is the channel measured to fail open. G-5 asks that hooks be POSIX `sh`; this is a guard of this repository's own, like `scripts/check-*.py`, not one of the plugin's `hooks/*.sh` gates.
- Affected modules and files, per .steering/structure.md:
  - New `scripts/claude-hooks/gh_guard.py`, `scripts/claude-hooks/gh_guard_lib.py` and `scripts/install-gh-hook.sh`; `scripts/check-leakage.sh` (the registration check). Nothing under `scripts/git-hooks/`, where every script becomes a hook the tree scan demands.
  - `scripts/test-gates.sh`, the leakage section, cases from 448, in two layers. One in-process harness, written to a file from a quoted heredoc at the top level and run once, imports `gh_guard_lib` and asserts about 180 inputs' decisions, reasons and source labels, with the guard call recorded rather than run; it runs under the registered interpreter where one is installed and under `python3` elsewhere, and the case says which. About twenty end-to-end runs feed the real entry script a hook input on standard input with the real guard. `leak_repo` and every fixture home a tree-mode case uses register the hook and hold `scripts/claude-hooks/` under `.git/info/exclude`, so the existing cases keep their counts; the suite unsets `CLAUDE_CONFIG_DIR` and `XDG_DATA_HOME`. Case 445's scan for `--no-hook-check` widens to `scripts/claude-hooks/`, which never holds that string. Case 429's pinned `CONTRIBUTING.md` strings gain the install command and the exempt list's path. No statement-position `assert` in the embedded Python.
  - `CONTRIBUTING.md`; new `docs/decisions/ADR-13-…`; `docs/CONTRACT.md` (M-1's row widens to what this maintainer's sessions publish with `gh`); `docs/verified.md` (a Claude Code section with an outcome per AC, the desktop terminal tool included, and the version row moved to 2.1.325, with the desktop app's bundled 2.1.321); `docs/fidelity.md` ("deny a tool call", exercised by this repository's own hook, not by anything the plugin ships); `.steering/structure.md` (the `scripts/` row); `.steering/tech.md` only if the suite needs a larger budget.
  - `docs/BACKLOG.md` records #361's discharge with its pull request's number, after the receipt, as #360's did; the row it empties is the next refinement's.
- Contract changes, and who else consumes them:
  - The working-tree guard also fails on a machine with Claude Code and no registered hook. Consumers: every session and contributor in this repository; a contributor without Claude Code is unaffected. CI is exempt.
  - The guard's `--text` mode gains a caller outside this repository's checkouts, and its `LEAK` and `WARNING` lines are parsed by it; a case pins their shape.
- Risks and trade-offs:
  - **A broken install blocks every Bash call in every session,** by the clarification's choice. The Edit tool still reaches `~/.claude/settings.json`, and the block names the cause.
  - **The order of the maintainer's steps matters.** Registration before the exempt list scans every private project's writes against the private patterns, and blocks many. T8 measures the hook with `--settings` first; the maintainer then writes the exempt list; only then is the hook registered and the check committed, before that turn ends, on the maintainer's go.
  - **The switches AC10 lists pass the hook in silence,** in any project. The registration check sees this repository's and the user-level ones, and nobody else's.
  - **The work in progress of this spec itself** is the reference while the default branch lacks the hook, so each review fix on this branch is installed for every session on the maintainer's go, as #360's hooks were.
  - **The interpreter is not verified for 3.9 in CI,** where `python3` is newer. The in-process harness runs under the registered interpreter on the maintainer's machine, and the check's probe runs it at every turn end.
  - **A body file can change between the hook's read and `gh`'s,** if a background job or another session writes it. Not closed.
  - **The lexer is the attack surface.** It errs closed: a `gh` word it cannot explain blocks. A false block costs one rewritten command; a false pass costs a public leak. AC9's replay counts the false blocks.
  - **A `gh` upgrade can add a flag** that reads a file or an editor; the table blocks unknown flags, and a version change warns until the table is regenerated.
  - **The suite's budget.** Five full runs took 273 to 306 s against 336 (the last work log), so the two-layer cases, about 6 s, fit; T10 measures before and after.

## 3. Tasks (TDD-ordered)
> One task is one complete Red-Green-Refactor cycle, so one green commit. No task is sequenced after the review.
