# Spec: A post-review task disarms the review gate
- Slug: 113-post-review-task-disarms-the-gate   Issue: 113   Type: bug   Status: approved
- Author: m0m0i   Date: 2026-09-10

## 1. Requirements (WHAT / WHY)
- Reproduction: on a spec branch, write a Tasks section whose last task is deliberately sequenced *after* the review — the version bump, as `.steering/tech.md:16-20` prescribes. Tick every task but that one and end a turn. `hooks/review-gate.sh:55` reads one unticked box and exits 0. Repeat for every turn of the review: the gate is silent throughout, and arms only once the bump is ticked, which by then is after the reviewer has already run.
- Expected: the review gate blocks a turn whenever a spec branch has no reviewable work left and no fresh CLEAN receipt — for every spec shape this project's own documents tell an author to write.
- Actual: for a spec carrying a post-review task, the gate passes on every turn from "implementation complete" until after the review is finished. The review still happened on #105, but it was procured by `skills/implement/SKILL.md` and by convention, not demanded by the hook.
- Impact: every spec that changes a shipped path and follows `.steering/tech.md`'s post-review bump — which is most specs in this repo, and every install that copies the same steering note. It is not a fail-open in the usual sense: no bad receipt gets through, and a spec that ticks everything still arms. It is narrower and worse-placed. `.steering/product.md` states the claim this repository exists to make — "The review gate is enforced by a hook, not requested by prose" — and for this shape the claim is false. A gate whose enforcement holds only for specs whose last task happens to precede the review is guidance wearing a hook's clothes, and it reads as working from the outside, which is the survival property that made #1, #14 and #16 expensive.
- **Root cause:** the gate's arming condition is a *proxy*. Zero open tasks stands in for "implementation is finished", and that proxy is sound only while every task is implementation work. `.steering/tech.md:16-20` introduced a second kind of task — work deliberately sequenced after the review — and nothing reconciled it with the proxy. The two rules were written against different questions: line 55 answers "is the model still mid-loop?", the steering note answers "what re-stales a receipt?", and neither was read against the other. So the project's own steering instructs authors to create the one state in which its one enforced rule cannot see them. #105 is where it first showed, not where it was introduced; the reviewer found it while checking whether that branch's deferral of T5 was itself sound. The deferral is sound.
- Acceptance criteria:
  - [ ] **AC1:** WHEN a spec is authored from the shipped templates THE SYSTEM SHALL sequence no task after the review, so that a spec with no unticked tasks always means the reviewer is due.
  - [ ] **AC2:** WHEN the reviewer's receipt is CLEAN and the branch changed a shipped path THE SYSTEM SHALL bump both manifests as a step of `implement`, in the same family as the work-log entry and the `Status: done` flip.
  - [ ] **AC3:** WHEN `skills/implement/SKILL.md` no longer carries that step THE SYSTEM SHALL fail a validator naming the file.
  - [ ] **AC4:** WHEN a live spec's Tasks section names work sequenced after the review THE SYSTEM SHALL fail a validator naming that spec, and specs under `.specs/_archive/` SHALL NOT be scanned, being records rather than instructions.
  - [ ] **AC5:** the regression tests fail before the fix and pass after.
  - [ ] **AC6:** THE SYSTEM SHALL leave `hooks/review-gate.sh` unchanged in behaviour — silent on a spec with no tasks written, on a mid-implementation turn, on an already-merged branch and on a non-spec branch; blocking on a fully-ticked spec with no receipt. A gate that starts firing on ordinary turns is a gate that gets switched off.
  - [ ] **AC7:** WHEN this change is committed THE SYSTEM SHALL carry a version bump in both manifests, `skills/` being a shipped path — performed as the new step, not as a task.
- Out of scope: #35 (`reviewed_sha` naming the working tree rather than the reviewed commit) — a separate defect in the same receipt. The duplication between `Source globs` and `check-version-bump.py`'s `SHIPPED` tuple, recorded on #14. Making `plugin.json` reviewable by adding it to `Source globs`, which ADR-3 settled and which this bug does not reopen. The receipts and specs already written, which are records.

### Clarifications
- 2026-09-10 — **Which of the issue's four options?** Option 3, generalised from the version bump to any post-review work: section 3 is implementation-only *by definition*, so "zero open tasks" once again means "the reviewer is due" and `hooks/review-gate.sh` is not touched. This is #10's precedent applied to the same class of problem. #10 did not teach the gate to recognise a half-task; it redefined a task as one complete Red-Green-Refactor cycle so that half-tasks cannot exist, then pinned the definition with `check-templates.py`. Option 2's marker was rejected on the same reasoning: it adds vocabulary whose omission re-opens the hole exactly as today, so it moves the failure rather than removing it. Option 1 is the dishonest tick. Option 4 cannot work — mid-implementation there is no receipt at all, so an arming rule based on receipt staleness would block every ordinary turn.
- 2026-09-10 — **Where does the guard live?** Both. `check-skill-contracts.py` gets a tenth entry pinning the new step in `skills/implement/SKILL.md`, and `check-templates.py` is extended to fail on a live spec whose Tasks section names post-review work. They guard opposite directions of rot — the instruction being edited away, and a spec written past an instruction that is still there — and only the first reaches consumers, since `scripts/` is not shipped while `skills/` is. The argument `check-skill-contracts.py`'s docstring demands of a tenth entry is that review cannot defend this sentence: the sentence's absence is invisible in a diff of `implement`, and its absence restores a silent gate rather than producing a visible defect, which is the shape review reliably misses.
- 2026-09-10 — **Patch or minor?** Minor: 0.4.4 → 0.5.0. #47's precedent argues patch, the shipped surface here being prose under `skills/`, but #52's argues minor and wins — this moves where the version bump sits in the flow, which is a change to the prescribed process and not merely its wording. A major bump is reserved for the minimum/full install switch, and is not this.
- 2026-09-10 — Answered from the repo, not asked: `hooks/templates/` holds only the two harness settings files and a README, so there is no second copy of the gate to keep in step. `check-templates.py` is already on the `Validators` line and already parses Tasks blocks by heading, so extending it keeps the guard count at nine, which is what #54 asks for.

## 2. Design (HOW)
- Fix approach, and why this rather than the narrower or wider fix: make "a task" mean pre-review work by definition, remove the one thing the project told authors to sequence after the review, and pin both halves. The narrower fix — moving the bump and saying so once in `implement` — leaves the rule as unguarded prose, and prose with nothing checking it is what produced this bug: `.steering/tech.md:16-20` was itself correct prose that nothing reconciled with the gate. The wider fix — teaching the gate a post-review marker — was rejected in the Clarifications for adding vocabulary whose omission re-opens the hole. The gate is not touched at all, which is the point: its rule was never wrong, the vocabulary underneath it was.
- Affected files:
  - `skills/implement/SKILL.md` — the bump as a numbered step in "Review gate — mandatory", after the receipt is written and beside the work-log entry and the `Status: done` flip; and the closing Rules bullet that already lists the commits landing after the review gains the bump.
  - `skills/spec/templates.md` — the shared note above the three Tasks blocks states that no task is sequenced after the review.
  - `.steering/tech.md:16-20` — "lands *after* the review" becomes "lands after the review, as a step of `implement` rather than as a task", so the paragraph stops prescribing the shape it caused. Its ADR-3 rationale for excluding the manifests from `Source globs` is unaffected and stays.
  - `scripts/check-skill-contracts.py` — the tenth `CONTRACTS` entry, and the docstring's "Nine today" moves to ten.
  - `scripts/check-templates.py` — the live-spec scan, reusing `tasks_by_section`.
  - `scripts/test-gates.sh` — the cases that prove both guards.
  - `.steering/structure.md:19`, `README.md:41`, `README.md:156`, `README.ja.md:43`, `README.ja.md:157`, `CONTRIBUTING.md:21` — the suite's path count, which the new cases move off 62.
  - `plugin.json`, `.claude-plugin/plugin.json` — 0.4.4 → 0.5.0, after the review, as the new step and not as a task.
- **Blast radius:**
  - `check-templates.py` is on the `Validators` line, so it runs at every turn end through the quality gate. A false positive blocks every turn in this repository, so the scan matches only a task line naming the review or a version bump, and it reports the spec by path and line rather than failing wholesale.
  - **`.specs/_archive/` must be excluded.** #105's T5 is precisely the forbidden shape, and it is a record of what was done, not an instruction. Rewriting it to satisfy a guard added afterwards makes the file useless as evidence — the #102 precedent, and the same reasoning that leaves `docs/verified.md`'s counts alone.
  - A repository with no `.specs/` at all, or a spec with no Tasks section yet, must pass rather than fail: that is the state `spec` step 3 tells an author to create, and it is the same false block as #8. A spec that exists and cannot be *read* must fail closed, because existence is not readability — #16, and the reasoning already written into `review-gate.sh:22` and `check-templates.py`'s own read error.
  - `check-templates.py`'s current subject is one shipped file. Widening it to this repository's own `.specs/` means the guard now has two subjects with different lifetimes, and only the first ships. The failure messages must say which subject failed, or a consumer reading a copied script will look for a `.specs/` rule that does not apply to them.
  - `skills/` is a shipped path, so `check-version-bump.py` requires the bump and CI fails the PR without it. That check is red from the first task until the post-review step runs; it is CI-only and blocks no turn, stated here so a mid-branch reader knows it is expected — the #52 precedent.
  - The path count is a claim in six live places today. #105's lesson is that a hand-listed set of directories missed one: the re-enumeration is `git grep` across all tracked files. Records are not corrected — `docs/verified.md`'s rows, the `.work_logs/` entries, and the `observations.md` lines in every spec directory each state what a run observed on its date.
  - The gate is untouched, so AC6 costs no new code; the existing suite already pins those paths and must stay green.
  - **This spec's own Tasks section is the matcher's hardest case.** T1 and T3 contain the phrases "post-review work" and "sequenced after the review" while being ordinary pre-review tasks that *build* the guard. A scan that greps those phrases flags the spec that introduces it, and the tempting repairs are both wrong: narrowing the phrase list until this file passes tunes the guard to one document, and exempting the spec that owns the guard exempts exactly the file most likely to get it wrong. The matcher has to separate a task that defers *itself* from a task that merely names deferral, which is what T1's cases pin.
- Why this cannot recur: the class is closed from three sides rather than one. The definition changes, so a post-review task is no longer a legitimate thing to write; `check-skill-contracts.py` fails if the instruction that says so is edited out of the shipped skill; and `check-templates.py` fails if a live spec writes one anyway. The proxy the gate depends on — "an unticked box means implementation is unfinished" — is stated once, in the templates, and guarded on both the instruction and the outcome. What remains uncovered and is worth naming: a consumer project's own specs are checked by neither guard, because `scripts/` does not ship. They get the corrected templates and the corrected `implement`, which is the same protection they have for every other rule in the harness.

## 3. Tasks (TDD-ordered)
> One task is one complete Red-Green-Refactor cycle, so one green commit. No task is sequenced after the review.

**AC7 is discharged by a step, not by a task, and that is the fix demonstrating itself.** No task below bumps the version; `implement`'s new post-receipt step does it, so this branch is the first to run the flow it prescribes. A reviewer reporting coverage by id should read AC7 against the receipt and the manifests, not against the task list.
