# Spec: the copied checks find `gate-lib.sh` from the session's own shell, and `init` states the whole 0.23.0 migration
- Slug: 263-copied-checks-find-gate-lib-from-any-shell   Issue: 263, with #264   Type: bug   Status: draft
- Author: m0m0i   Date: 2026-10-08

One spec for two issues, as `docs/BACKLOG.md` row 1 directs: they have one cause, and #263's re-copy is half a fix while the re-copied check still fails by hand (#264). The branch is named for #263; #264 closes with it.

## 1. Requirements (WHAT / WHY)

- Reproduction: re-measured at `9dd73bc` on Claude Code 2.1.293, in a scratch git tree with `.steering/` and no `hooks/`, `.claude/hooks/` or `.agents/hooks/` — the tree `init`'s migration leaves.
  1. **#263.** The 0.22.0 copy of `scripts/check-steering-anchors.sh` (from the cached 0.22.0 plugin) exits 1, `cannot find gate-lib.sh in hooks/, .claude/hooks/ or .agents/hooks/`, with `CLAUDE_PLUGIN_ROOT` unset and with it set to the installed 0.23.1. That copy is what a project keeps after applying step 3's migration bullet as written, so the plugin's quality gate blocks every turn that changes source, and CI that runs the check fails.
  2. **#264.** The branch base's copy exits 1 in this session's own Bash tool, where `CLAUDE_PLUGIN_ROOT` and `GATE_SDD_HOOKS` are both unset, and exits 0 with `CLAUDE_PLUGIN_ROOT` set. The quality gate passes at turn end; `implement`'s loop and every reviewer see exit 1 for the same tree. `assets/check-unreviewed-work.sh` has the same lookup.

- Expected: one verdict for one tree, wherever the check runs. Step 4.1 of `skills/init/SKILL.md` requires the gate be armed on a green tree; `skills/implement/SKILL.md` runs the validators inside the loop; `reviewers/_shared/reviewer-contract.md` asks every reviewer to run "the project's own validators" and rates a failing one at least HIGH.

- Actual: as reproduced. #263 lists what two downstream migrations had to do beyond the bullet; #264 measured the hand run on 2.1.292.

- Impact: #263 is every Claude Code project migrating from before 0.23.0. #264 is every Claude Code project at 0.23.x, fresh installs included, since none has a copy of the library any more: every `implement` run and every review. Both fail closed, so neither is a fail-open; what they cost is a reviewer returning non-CLEAN for a tree the gate passes, and an author who learns to ignore one failing validator. Row 6 waits on this, and every gate fix below row 1 reaches a project only once it has migrated.

- **Root cause:** since 0.23.0 (#256) a check `init` copies into the project depends on a library only the plugin ships, and none of the places the copy looks resolves from the session's own shell. `CLAUDE_PLUGIN_ROOT` is set for a plugin's hooks and, by Claude Code's own documentation, "aren't present in the environment of commands Claude runs through the Bash tool, in the main session or in a subagent" (`plugins/manifest-reference`, "Where each variable resolves"). #256's Q1 chose discovery by environment and named the two paths it covered, turn end and CI; the session's shell is the third, and it is where `implement` and the reviewer run. #263 is the same cause seen from the migration: step 3's bullet was written as the gate half of #256's AC5, and never says that the project's copies of the two checks predate the lookup, that every CI job running them needs the plugin, or that the project may own other readers of the files it deletes.

### Clarifications

Asked and answered 2026-10-08. Both mechanisms in Q1 were measured before asking, in a scratch plugin on Claude Code 2.1.293 (`docs/verified.md` gets the record, AC6).

- **Q1. How do the copied checks find the plugin's library from the session's own shell?** The plugin's `SessionStart` hook appends an `export` to `CLAUDE_ENV_FILE`, and the checks read that variable at the plugin's rank. The alternative was a plugin `bin/` locator on the Bash tool's `PATH`, which is documented, but "claude.ai and Cowork don't install a plugin that has a top-level `bin/` directory" (`plugins/components`, Executables), and this plugin's top level is the repository root. → AC1, Design.
- **Q2. Does "an ordinary shell" include a person's own terminal, outside any Claude Code session?** No. Inside a session it is automatic. A terminal outside one sets `GATE_SDD_HOOKS`, and the check's error says how. → AC3.
- **Q3. Which project does the AC6 run migrate?** A real Claude Code project of the maintainer's at 0.22.0, on its own branch, with a pull request there so its CI actually runs. The project was not named at clarify. It is asked before the run, together with the go-ahead to push to that repository. → AC6.
- **Not asked, because the repo answers it:**
  - The version bump is a **minor**, 0.24.0: `init`'s migration flow moves and both checks gain a variable they read. #256 was 0.23.0 for the same kind of change, and `implement` makes the bump as a step.
  - The decision gets **ADR-9**, and ADR-8 gets a dated consequence line pointing at it, as ADR-2 did for ADR-7 (`99e1591`).
  - The migration **re-copies the two checks**, since without that the project is broken. The project's other copies are compared with the plugin, as the README's update section already says.
  - The variable's name and rank are Design's.

## 2. Design (HOW)

- **Fix approach.** The plugin tells the session's shell where it is, and the checks look there last.
  1. **`hooks/plugin-gate.sh` writes one line on `SessionStart`.** When the event is `SessionStart` and `CLAUDE_ENV_FILE` is set, it appends `export GATE_SDD_PLUGIN_ROOT='<root>'`. `<root>` is the parent of the wrapper's own resolved directory, single-quoted with any `'` escaped. It skips the append when the last `GATE_SDD_PLUGIN_ROOT` line already in the file is identical, because the probe showed the file is kept across `--resume` and `/compact` and gains a line on every `SessionStart`. It writes nothing when the root contains a newline. A failed write is silent: `SessionStart` has no blocking channel, and the failure lands where it is loud anyway, as AC3's error. The write happens **before** check (1) and check (2). `init` runs in a session that began before `.steering/` existed, and a migration runs in one where the digest stood down, and both need the variable for step 4's by-hand run. A variable that nothing reads is inert in a project that does not use the harness. Stop events never write, and Claude Code does not offer them the file anyway.
  2. **The two checks read it at the plugin's rank.** The order is `GATE_SDD_HOOKS`, then `hooks/`, `.claude/hooks/`, `.agents/hooks/`, then `$CLAUDE_PLUGIN_ROOT/hooks`, then `$GATE_SDD_PLUGIN_ROOT/hooks`. The last two name the same loaded plugin from two places. The quality gate `eval`s each validator inside the hook's own environment, which has `CLAUDE_PLUGIN_ROOT` and not the env-file variable (the probe's `Stop` hook saw no `GATE_SDD_PLUGIN_ROOT`). The session's shell has the env-file variable and not `CLAUDE_PLUGIN_ROOT` (documented, and measured above). So exactly one of the two is set in each place, and the two places get one verdict (AC1). The error names all six places and the value of each variable that is set. It ends by saying that outside a Claude Code session the remedy is `GATE_SDD_HOOKS` (Q2).
  3. **`init` states the migration whole (AC4) and verifies it from the session's shell (AC5).** The migration bullet keeps its first sentence, then adds the steps AC4 lists. Step 4.1 runs every gating validator by hand in the session's shell and the quality gate as `sh "$GATE_SDD_PLUGIN_ROOT/hooks/plugin-gate.sh" quality-gate.sh`. If the variable is unset, the plugin was not loaded when the session started, and the step says to restart, as 4.4 does for the reviewer. The unreviewed-work bullet's closing sentence about a by-hand run says the same as the check's error.

- **Rejected, and why.** The backlog row's options and the measurements behind each:
  - **Resolve the plugin from `installed_plugins.json`** (#264's first direction). Claude Code documents the file's fields but gives no stability promise for it. A project can also carry more than one entry: this machine holds two at two versions (user scope 0.23.1, one project's scope 0.23.0) and six cached versions, and which one loads in a project with both is V4's open question. A wrong guess reads a library older than the gate's, so the check could pass where the gate blocks. Under `- Owns: gates never fail open` that is the wrong direction to fail.
  - **The digest prints the path, and `implement` and the reviewer contract export it** (#264's second direction, as written). This puts a rule in the layer that can be talked out of it. Every Bash call is a fresh shell, so the export would have to ride on every command. The reviewer is copied into the project rather than loaded as plugin content, so even `${CLAUDE_PLUGIN_ROOT}` substitution would not reach its text. The chosen fix is this direction moved down into the hook layer.
  - **`init` writes `GATE_SDD_HOOKS` into the project's settings `env`** (#264's third direction). The value is an absolute path under one person's home and one version's cache directory. Committed, it is wrong for every other contributor. In `settings.local.json` it goes stale at every auto-update, and stale is worse than absent here, because old cache directories stay on disk (all six above still do): the path keeps resolving to yesterday's library with no complaint. Claude Code does not document variable expansion in `env` values. And `GATE_SDD_HOOKS` outranks every local copy.
  - **`init` copies `gate-lib.sh` again** (the sixteenth refinement's expectation). ADR-8 already rejects this: "the same drift, in the file that holds the fixes." Worse, a copy outranks the plugin, so at turn end the check would ask the copy's question while the gate asks the plugin's. Moving the plugin ahead of the copy would split the by-hand run from the turn-end run, which is #264 again, and would put this repository on an installed library instead of its source.
  - **The checks carry the reader they need.** A copy of the question that can disagree with its subject is #14 and #23, and `.steering/tech.md` states the rule that both checks ask `gate-lib.sh`. `check-unreviewed-work.sh` alone calls six of the library's functions. A copy carried in the project's `scripts/` is refreshed only by `init`, which is the drift ADR-8 measured at 90 to 377 lines.
  - **Write `GATE_SDD_HOOKS` itself into the env file.** It is read first, ahead of the copies, so a dual-target project would read the plugin's library by hand and its `.agents/hooks/` copy at turn end. The env file is also sourced before each command, so it would override a person's own explicit export.
  - **Ship the checks from the plugin, as ADR-8 did the gates.** This would remove the re-copy entirely. But the `- Validators:` line is one line that both harnesses' gates run. In a dual-target project, or in a terminal, a plugin path resolves nowhere, and the run fails with the shell's "not found" instead of the check's own message about what to set.
  - **A plugin `bin/` locator** was Q1's alternative.

- **Affected files:** `hooks/plugin-gate.sh`; `assets/check-steering-anchors.sh` and `assets/check-unreviewed-work.sh` (lookup, comments, error text); `scripts/test-gates.sh`; `scripts/check-skill-contracts.py`; `skills/init/SKILL.md`; `docs/decisions/ADR-9-the-plugin-tells-the-session-shell-where-it-is.md` (new) and ADR-8's dated line; `docs/verified.md`; `README.md` and `README.ja.md`; both manifests at the bump.

- **Blast radius:**
  - **`scripts/test-gates.sh` stops inheriting the caller's environment.** Once the installed plugin carries this change, every Bash call in this repository's sessions has `GATE_SDD_PLUGIN_ROOT`, and cases 215 and 216's "nowhere" halves would find the installed library and pass. Worse, a `plugin-gate.sh` case run from a session could append to that session's real env file. The suite therefore unsets `GATE_SDD_HOOKS`, `GATE_SDD_PLUGIN_ROOT`, `CLAUDE_PLUGIN_ROOT` and `CLAUDE_ENV_FILE` at the top, and each case sets only what it means.
  - **This repository** still reads `hooks/` from source, because the directories come before both plugin variables, and the installed plugin's write happens before it stands down here. No change to ADR-6.
  - **Un-migrated, Antigravity and dual-target projects** read their own copies first, as before.
  - **Cases 205 to 209** (the wrapper) keep their verdicts. The write comes before check (1) but produces no output, so case 206's "no sound" still holds. AC2 already holds 215 and 216.
  - **CI is unchanged.** `GATE_SDD_HOOKS` still comes first.

- **Why this cannot recur:** the session's shell becomes a place the suite tests by name (T1, T2), next to turn end (case 205) and CI (215, 216), so a lookup that loses any of the three goes red. `check-skill-contracts.py` pins the migration's sentences, which a review would otherwise read as trimmable. **Not closed:** a copied check can still fall behind the plugin in some future release that changes the lookup again. The library-version guards report a library older than the check. Nothing reports a check older than the plugin except the README's comparison command, and a digest line for that is separate work.

- **Limits, recorded rather than fixed:** a mid-session `/reload-plugins` after an update was not measured. If it does not fire `SessionStart`, the env file keeps the old root until the next one, and old roots stay on disk, so the by-hand run reads the previous version's library until then. `CLAUDE_ENV_FILE` for a plugin's hook is measured rather than documented. If a later version withdraws it, AC3's error is the result, not a pass. ADR-9 carries both.

- **Open question for `implement`:** the AC6 run must load this branch's plugin, not the installed 0.23.1, in a project whose migrated settings enable the installed one. The isolation method (a plugins root of its own, as #257's M2c used) is chosen at the run and recorded with it.
