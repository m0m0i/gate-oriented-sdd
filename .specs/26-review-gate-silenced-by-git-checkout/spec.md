# Spec: the review gate is silenced by `git checkout`

- Slug: 26-review-gate-silenced-by-git-checkout   Issue: 26   Type: bug   Status: approved
- Author: m0m0i   Date: 2026-09-20

## 1. Requirements (WHAT / WHY)

- Reproduction: on a spec branch with every task in section 3 ticked and no `.specs/<slug>/.review-receipt`, `sh hooks/review-gate.sh` exits 2 and names the missing receipt. Run `git checkout main` — nothing pushed, merged, reverted or stashed, the branch still at the same commit — and the same command exits 0 and prints nothing on either channel.
- Expected: the one rule this harness enforces rather than requests is not disabled by a routine, non-destructive command that leaves the unreviewed work exactly where it was. `README.md:7` and `README.md:23-29` make enforcement the reason the project exists, and `.steering/product.md`'s `- Owns: gates never fail open` is the anchor every severity is judged against.
- Actual: the gate exits 0 and writes nothing anywhere. A skipped review and a repository holding no unreviewed work produce byte-identical output — silence — so afterwards there is no way to tell them apart, in the working tree, in the history, or in CI.
- Impact: every project, on the only layer `README.md:23-29` marks **No** in the "Can it be skipped?" column. The bypass costs one command, needs no flag, and leaves no artefact. It was reached three times in one session while #27 was open, each time disclosed in the transcript and nowhere else — the repository itself records none of them. This is the fail-open shape already paid for twice, in #1 and #16, and the third time it is the escape rather than the check.
- **Root cause:** `hooks/review-gate.sh:19-22` derives the subject of the check from `git rev-parse --abbrev-ref HEAD` and then asks *"is there a spec for the branch I am standing on?"*. That is not the question the claim makes; the claim is about *"does this repository contain finished work nobody has reviewed?"*. Binding the first to the second is only sound while the branch name is fixed, and it is not: it is author-controlled state that a non-destructive command rewrites in milliseconds. So the domain of the enforced rule is selected by the party the rule is enforced against — and because a branch with no spec is overwhelmingly the common case, the gate's response to that selection has to be silence, which is also exactly what a bypass looks like. The narrowness at `:22` is deliberate and load-bearing (`README.md:41-43`), so the defect is not that the line returns early; it is that no caller asks the repository-wide question, and no layer the author cannot step out of asks it either. CI has the branch, the spec and the receipt in view on every pull request and reads none of them.
- Acceptance criteria:
  - [ ] **AC1:** WHEN a turn ends, AND the repository holds a local branch that is not merged into the base, whose `.specs/<branch>/spec.md` has at least one task in section 3 and no unticked one, and which has no `.review-receipt` recording `verdict=CLEAN` at a commit from which no path matching `- Source globs:` has changed, THE SYSTEM SHALL block the turn on both harness channels, naming each such branch and what would clear it. This SHALL be asked on **every** branch, after the current branch's own spec has been checked as it is today — not only where the current branch has no spec of its own, which would leave `git checkout -b` onto a directory holding a task-less spec as a second one-command bypass.
  - [ ] **AC2:** WHEN no branch satisfies AC1, THE SYSTEM SHALL stay silent and add no delay a person would notice. Silent specifically for: a spec still being implemented, a spec whose receipt is CLEAN and not stale, a spec branch merged into the base, a spec whose branch no longer exists locally, and a `.specs/` directory holding no `spec.md` — the last being real debris on `main` today (`.specs/109-minimum-set-in-one-unit/`). The clean-tree round trip to the default branch that both the author and `gate-sdd-reviewer` needed for a baseline measurement within one session (#26's comment) SHALL remain silent, because a mid-implementation branch is silent under AC1.
  - [ ] **AC3:** WHEN a pull request's head branch has a spec with at least one task and no unticked one, and no CLEAN, non-stale receipt at the head commit, THE SYSTEM SHALL fail a CI check that takes the head branch and head commit from the pull-request event rather than from `HEAD`, so that moving `HEAD` cannot satisfy it. WHEN the head branch has no spec directory, the check SHALL pass and SHALL say what it examined rather than printing a bare success.
  - [ ] **AC4:** AC3's check SHALL ship. It lives in `assets/`, and `init` SHALL copy it into the project and instruct that it be added to the project's CI beside the other validators, stating why it is deliberately not on the `- Validators:` line.
  - [ ] **AC5:** AC3's check SHALL ask the gate's own questions by calling `hooks/gate-lib.sh` rather than re-implementing them, and SHALL exit non-zero with a diagnostic — never pass — when it cannot locate that library or the library predates the function it needs. This is `assets/check-steering-anchors.sh`'s contract and #16's shape.
  - [ ] **AC6:** THE SYSTEM SHALL record the decision on #36 in writing, answering its three stated questions, and the tracker SHALL be updated to match that decision.
  - [ ] **AC7:** `README.md` and `README.ja.md` SHALL carry no claim stronger than the mechanism that lands, and the sentence in each asserting that the review gate reads only the current branch's spec and cannot see a shipped spec left in `.specs/` (`README.md:74`, `README.ja.md:111`) SHALL be corrected — it becomes false under AC1 — with the two files making the same claim.
  - [ ] **AC8:** every behaviour in AC1–AC5 SHALL have a case in `scripts/test-gates.sh` that fails before the change and passes after, and no pre-existing case SHALL change verdict. _Amended 2026-09-20, during T1, with one named exception._ Case 9 (`non-spec branch stays silent`) builds a repository whose `9-feature` branch is finished and unreviewed and then stands on `unrelated` — which is the bug's own state, asserted as silence. Its **verdict and its stated intent are preserved** by re-basing its fixture onto a branch that is still mid-implementation, so it goes on proving that a branch with no spec is not gated on its own account; what it must stop proving is that parked unreviewed work is invisible, which AC1 now asserts the opposite of. No other pre-existing case changes fixture or verdict. _Second amendment, same pass:_ the AC2 half of the new cases (80-83) **passes before the change**, because today's gate is unconditionally silent off-branch — they are red-capable only against a scan that over-fires, which is the standing `scripts/test-gates.sh:230` already has for the same reason. The AC1 half (76-79) fails before and passes after, as written.
- Out of scope: **#36's `PreToolUse` gate itself** — decided here (see Design), built elsewhere if at all. **#35** (a by-ref review records the working tree's `reviewed_sha`) — the same receipt field, a separate fail-open with its own regression risk. **#39** (guards that report success they did not earn) — this work must not manufacture a pass, but the project-wide vocabulary for "I checked nothing" is that issue's. **Branch protection requiring the new check** — a repository setting, not harness work, and unverifiable from a session; it is already carried in the work logs and `docs/BACKLOG.md:31`. **A push straight to `main` that opens no pull request** — no layer in this spec sees it; named as residual under Blast radius rather than silently left out.

### Clarifications

Asked and answered 2026-09-20, before any Design existed. Two of the three changed section 1.

1. **Where should the guarantee live, and who receives it?** — *Answered: a CI check, shipped to installs.* The checker goes in `assets/`, this repository wires it into `ci.yml`, and `init` copies it and instructs the operator to add it to their CI — the seam `assets/check-locks.py` and `assets/check-document-set.py` already use, so the harness ships a checker rather than an opinion about anyone's CI. Rejected: CI in this repository only (leaves every install with the hole, and forces the README to describe its own gate as advisory), hook-widening alone (a hook is still a thing you can switch off), and documenting the bypass without fixing it. **Added AC3, AC4 and AC5.**
2. **At turn end, with no non-blocking channel available on either harness (`docs/verified.md:71-86`), what should the hook do about unreviewed work on another branch?** — *Answered: block, scoped to local branches not merged into the base.* Clearing it means writing the receipt, merging, or deleting the branch; deletion is destructive and visible, unlike `git checkout`, so there is no silent step around it. Rejected: scoping to the branch just left via `@{-1}` (a second checkout moves it, which converts a one-command bypass into a two-command one rather than closing it), writing a durable trace instead of speaking (adds state to a gate that has none, and is ignorable by construction), and leaving the hook alone. **AC1 changed from "emit a message" to "block", and widened during design from non-spec branches to every branch — see its own text for the bypass that forced it.**
3. **What does this spec do with #36, which `docs/BACKLOG.md:35` folds into this row?** — *Answered: decide in writing here, build separately.* **Added AC6**; the decision is in Design.

## 2. Design (HOW)

- Fix approach, and why this rather than the narrower or wider fix: **one question, asked in three places, defined once.** `hooks/gate-lib.sh` gains `gate_spec_review_state <spec-dir> <tip>`, which returns a machine-readable code — `unreviewed:no-receipt`, `unreviewed:verdict=<v>`, `unreviewed:stale=<files>`, or empty for "nothing to demand here" — and each caller composes its own message from it. `review-gate.sh` keeps its current branch-scoped path exactly as it reads today, message for message, and gains a second pass over the other `.specs/*/` directories once that path has cleared. `assets/check-unreviewed-work.sh` asks the same function about one branch named on the command line. The narrower fix — widening `review-gate.sh` alone — was rejected in clarification 1 because a hook can be switched off; the wider one — a `PreToolUse` gate on `git push` as well — is rejected below. Three call sites of one shell function is the shape `assets/check-steering-anchors.sh` already established for `gate_steering_value`, and it exists because a copy that can disagree with its subject is the defect class of #14 and #23.
- Affected files: `hooks/gate-lib.sh` (the shared question), `hooks/review-gate.sh` (the second pass), `assets/check-unreviewed-work.sh` (new, shipped), `.github/workflows/ci.yml` (a pull-request-only step), `skills/init/SKILL.md` (copy it, add it to the project's CI, keep it off the `- Validators:` line), `scripts/check-skill-contracts.py` (pin that instruction), `.steering/tech.md` (a sibling to the section explaining why `check-version-bump.py` is not a turn-end validator), `scripts/test-gates.sh` (AC8), `README.md` and `README.ja.md` (AC7), `docs/DESIGN.md:12,29-32` (the new seam and its guard). `plugin.json` and `.claude-plugin/plugin.json` move 0.14.1 → **0.15.0** as a step of `implement`, not as a task: `assets/` is shipped by prefix in `scripts/check-version-bump.py:31`, and a behaviour change to a gate is a minor bump.
- **Blast radius:**
  - **Every turn end in every project**, including turns doing unrelated work. This is the deliberate cost of the answer to clarification 2, and it is the repository's most-named failure mode (`README.md:41-43`): a gate that fires on ordinary turns gets disabled. What bounds it is that AC1's condition is a state the model can clear and that finished-but-unreviewed is short-lived by design — but a developer parking two finished branches for a week will be blocked on every turn for a week. `scripts/test-gates.sh` cannot detect annoyance; if this is felt in use, the honest response is to record it as a defect against this spec rather than to narrow the condition quietly.
  - **Turns on spec branch A are now blocked by finished, unreviewed work on spec branch B.** That follows from AC1 being asked on every branch, and it is the price of closing the `git checkout -b` variant of the bypass.
  - **`archive` and specs left in `.specs/`.** The scan reaches directories the gate previously could not see, which is why AC7 corrects both READMEs. Shipped specs stay silent through their CLEAN receipts and merged or deleted branches, not through invisibility — a weaker guarantee than the one the sentence claims today, and the sentence has to say so.
  - **Cost per turn** is one glob of `.specs/*/spec.md` plus, per candidate, a `git rev-parse --verify` and a `git merge-base`. The receipt checks short-circuit before any `git diff`, so the expensive call happens only for a branch that is finished and has a CLEAN receipt.
  - **Residual, stated rather than hidden:** a push straight to `main` opening no pull request passes every layer here. Only branch protection closes that, it is a repository setting, and it is out of scope above.
- Why this cannot recur: the class is *"a gate answers a question narrower than the claim it backs, and the difference is invisible because both look like silence"*. Three things make the difference visible. AC8 puts each silence case in `scripts/test-gates.sh` as a named case, so the next person to narrow the condition fails a test that says which claim they narrowed. AC5 makes the shipped checker fail closed when it cannot ask the question at all, so "could not check" stops resembling "checked and clean". And AC3 moves the load-bearing answer to a layer with no working tree to step out of — the author can silence the hook and cannot silence the pull request.

### Decision on #36 — not adopted; the push boundary is the weakest of the three points

Recorded here because `docs/BACKLOG.md:35` makes it part of this row, and answering its three questions in order:

1. **One enforcement point or two?** Two, but not the two #36 proposed: the widened `Stop` gate (AC1) and the pull-request check (AC3). The push boundary is a *third*, and with AC3 in place its marginal guarantee is the smallest of the three while its regression risk is the largest. A `PreToolUse` matcher sees only the pushes that pass through the tool call it matches; a person typing in a terminal, a push from an IDE, or `gh pr create` from another surface are invisible to it. CI sees every pull request regardless of who opened it or how.
2. **What is the message at the push boundary?** Moot unless it is built. The observation that made it attractive survives and is worth keeping on the record: at that boundary the author is definitely not mid-review, so the instruction could be unconditional — a luxury the `Stop` message does not have, and one AC3's CI message inherits for the same reason.
3. **Does a second point weaken the first?** Not the two that land, because they answer different questions — AC1 asks what the *repository* contains, AC3 asks what a *pull request* carries, and neither is the other's duplicate. A push gate would be a second answer to AC3's question, and that is precisely the configuration in which "the first is redundant" becomes arguable. So the risk #36 names as social rather than technical is real, and it is an argument against #36 specifically.

**Action:** **keep #36 open and demoted.** The spec recommended closing it; the author decided otherwise at approval on 2026-09-20, and the decision is recorded in that direction rather than the recommendation being quietly rewritten. Demoted means: not scheduled, nothing waits on it, and the three questions above are answered rather than open — what remains is a candidate third layer held against evidence. The tracker has no label for that state (`wontfix` would misstate it), so the comment required by AC6 is what carries it. Its falsifier is stated so it is revisited on evidence rather than on taste: if unreviewed work is observed reaching `main` by a route that is not a pull request, the push boundary becomes the cheapest remaining layer and this decision was wrong. `docs/BACKLOG.md:35` pairs #26 and #36 as one row on the expectation that the pair discharges together; it now half-discharges, and recording that is the next grooming's — see #79 and #174, which are about exactly this gap.
