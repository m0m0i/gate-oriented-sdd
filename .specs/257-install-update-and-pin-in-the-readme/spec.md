## 1. Requirements (WHAT / WHY)

- What changes: #257's **What changes**, plus what its comment of 2026-10-07 folds in from the unpublished migration playbook: the shape of its step 1 (how to tell whether a project is affected), its step 2 (the update commands on each harness), and the Antigravity half of its step 4 (refreshing what `init` copied). Three more changes come from #257's rule that every behavioural claim matches what shipped. `README.md:106` and its Japanese counterpart say `init` installs "the hooks" beside things that do not ship with the plugin, and on Claude Code the gates now do. `skills/init/SKILL.md` says `claude plugin install … --scope project` "writes the same entry" as the declaration, which M1 below shows it does not (Q4). And the README's declaration is tied to the template it quotes, so the two cannot drift apart silently (Design 2).

- **What must NOT change:** #257's **What must NOT change**, as checks. The `## Status` section of each README is byte-identical to the merge-base. `./scripts/check-readme-claims.py` exits 0. Every behavioural claim the new text makes carries one of three marks, defined once in the section: **verified** with the `docs/verified.md` entry or `scripts/test-gates.sh` case that produced it, **documented** with the Claude Code documentation page it comes from, or **not run**. No claim is marked verified on documentation alone, which is the README's own rule for the fidelity table ("Every row was produced by running it").

- Why now: #257's **Why now**. 0.23.0 shipped the mechanism on 2026-10-07, so a consumer can already reach the declaration through `init` and has no README that says why `autoUpdate` matters or what a pin does.

- What is already known, from the Claude Code documentation read on 2026-10-07 (`plugins/install`, `plugins/loading`, `settings-reference`, `cloud-environments`), from `docs/verified.md`'s #256 section, and from this spec's runs (Clarifications, M1 to M2c):
  - **Auto-update** is decided by the first of: `autoUpdate` on an `extraKnownMarketplaces` entry in a settings file; `autoUpdate` in `known_marketplaces.json`, which the `/plugin` toggle writes; the default, off for a third-party marketplace. Where several settings files declare one name, the highest-precedence file's entry is used whole. The pass runs in an interactive session after the first message, after a random delay of up to ten minutes, and the new version loads at the next launch or on `/reload-plugins`. `DISABLE_UPDATES`, `DISABLE_AUTOUPDATER` and `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC` turn the pass off unless `FORCE_AUTOUPDATE_PLUGINS=1`. A manifest that pins `"version"`, as this plugin's does, updates only when that string moves. Documented; no run here has waited for an update.
  - **What the install commands write** (verified, M1): `claude plugin marketplace add m0m0i/gate-oriented-sdd` writes the marketplace into the user's `extraKnownMarketplaces` with no `autoUpdate`; `claude plugin install gate-sdd@gate-oriented-sdd --scope project` writes `enabledPlugins` into the project's `.claude/settings.json` and nothing else.
  - **Project scope on a teammate's machine** (documented, not run): a project's `extraKnownMarketplaces` is honoured only after the folder's trust dialog, and a `-p` run in an untrusted folder ignores it without a message (M2b saw exactly that); a plugin enabled only in project settings is fetched only when its marketplace entry is a relative path, which this plugin's (`"./"`) is.
  - **A cloud session** runs the hooks in the repository's `.claude/settings.json` and installs none of the plugins it enables (documented, not run). So a project `init` migrated to 0.23.0 runs no gate in a cloud session, where its pre-0.23.0 copies did. Filed as #260 (Q3).
  - **Pins.** V3 (verified): a project-scope `#ref` under a marketplace name the machine already knows is ignored and does not move the shared clone. M2c (verified by the `--settings` route, trust step not run): on a machine that does not yet know the name, a pinned declaration is honoured; the clone is made at the tag, `known_marketplaces.json`, which is one per user, records the `ref`, and the plugin installs at the tag's version. Together: a project pin's effect depends on which declaration a machine met first, and once honoured it holds every project on that machine. M2a: the settings form of a pin is `"ref"` inside `source`, as `marketplace add owner/repo#ref` writes it.
  - **V2** (verified): the harness does not deduplicate a plugin hook against a project hook, so a second plugin id would run every gate twice unless something stands it down, and `hooks/plugin-gate.sh` stands down only for project settings entries. Whether two marketplace plugins with one manifest name both load is not documented.
  - **Tags.** Not every release is tagged: `gate-sdd--v0.22.0` and `gate-sdd--v0.23.0` exist, 0.22.1 and most of 0.21.x have none.
  - **Antigravity** (verified, run 2026-10-07): `agy plugin help` at 1.2.16 lists no update command. The playbook's uninstall-and-install path was checked with `agy plugin validate` only.

## 2. Design (HOW)

- **Approach, and the order of operations.**
  1. **The backlog first**, because filing #260 turned `./scripts/check-backlog-tracker.py` red on every branch: row 1's `Why here` gains one sentence citing #260 as this spec's finding, recorded rather than ordered, which is the form for an issue filed between refinements.
  2. **One guard ties the README's declaration to the template.** `scripts/check-readme-claims.py` gains a claim: each README holds exactly one fenced `json` block whose top-level keys are `extraKnownMarketplaces` and `enabledPlugins`, and both values equal the template's. It fails naming the README and the key that differs, and fails if no such block is found, so deleting the declaration is loud. This is the badge's argument from #133 applied to the next claim: the README quotes a file, and nothing else would notice the file changing. `scripts/` is not shipped. The fixture in `scripts/test-gates.sh` gains the template and a matching block in both READMEs so the existing cases keep their verdicts, and new cases cover a missing block, a changed `autoUpdate`, a changed plugin id, and the control. The first README text lands in the same task: the declaration and the two sentences around it, in both languages.
  3. **`docs/verified.md`**: a section after #256's, "What the install commands write, and V3's other branch (#257)", holding M1 to M2c as the Clarifications state them, with the scratch paths reduced to their roles. The version table names 2.1.292 for it, and **Still to verify** narrows V3's item to the trust-dialog step.
  4. **The README's `## Install`**, in both languages, in this order: Claude Code's install commands and `init`'s declaration (from step 2); **why `autoUpdate`**; **what each kind of drift does**, a table of Situation, What happens, and Evidence; **pinning**; **updating**; then Antigravity's install as it stands, and the closing `init` sentence. The fidelity table gains `Gate delivery` after the review-receipt row, worded as `docs/fidelity.md`'s without its status column.   5. **`docs/layout.md`**, both trees.
  6. **`skills/init/SKILL.md`**: the one sentence says `--scope project` writes only `enabledPlugins`, so it does not stand in for the declaration, and cites `docs/verified.md`.
  7. After review, as `implement`'s steps rather than tasks: 0.23.1 in both manifests, and the work log.
