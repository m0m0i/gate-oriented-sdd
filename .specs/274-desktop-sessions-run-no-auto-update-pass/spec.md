# Spec: Desktop-app sessions run no plugin auto-update pass, so a gate fix never reaches a machine used only through the app
- Slug: 274-desktop-sessions-run-no-auto-update-pass   Issue: 274   Type: bug   Status: approved
- Author: m0m0i   Date: 2026-10-10

## 1. Requirements (WHAT / WHY)

- Reproduction: #274's, which is #265's U2 to U4 in `docs/verified.md`. On a machine with the plugin installed and the marketplace declared with `"autoUpdate": true`, start a session from the Claude desktop app's Code tab and send a message. Its Bash prints `DISABLE_AUTOUPDATER=1` and `CLAUDE_CODE_ENTRYPOINT=claude-desktop`, and a `claude` started in a terminal prints neither. Past the documented ten minutes, `~/.claude/plugins/known_marketplaces.json` keeps its `lastUpdated`, and a release published before the session started is not installed. This spec's session reproduced the first half on 2026-10-10 at Claude Code 2.1.294: its own shell carries both variables, and a headless run started from it, with its own plugin root, logs `Plugin autoupdate: skipped (auto-updater disabled)` at startup.
- Expected: the README's **Why `"autoUpdate": true` is required** and ADR-8's first consequence. With the declaration `init` writes, a gate fix reaches a Claude Code project by plugin update, with no pull request in the project, and ADR-8 makes that update the only route a gate fix has.
- Actual: no session the desktop app starts runs the pass, so a machine used only through the app stays at the version it installed. 0.23.0 did not arrive for three hours, and 0.24.1 had not arrived sixteen hours after its release; both were updated by hand (U1, U4). Nothing in the harness says so.
- Impact: every Claude Code user of the harness who works only in the desktop app, the maintainer included, misses every gate fix released after their install, and nothing tells them. That is the drift ADR-8 removed, back in the form the README warns about. **Where the install predates 0.23.0, a gate fails open:** no version from 0.21.3 to 0.22.0 ships Claude Code hooks, and a migrated project has no copies left, so a turn there ends with no `Stop` gate and nothing says so. One of the maintainer's two machines was at 0.21.8 on 2026-10-09. The eighteenth refinement read this from the cached manifests and did not run it. Under `- Owns: gates never fail open`, which is why this is row 1.
- **Root cause:** four parts, each necessary.
  1. The desktop app starts every Code-tab session with `DISABLE_AUTOUPDATER=1` in the launch environment it builds (U2). Why is not documented. The variable's documented subject is Claude Code's own binary, which the app downloads and updates itself (`desktop`), and the app's page says nothing about plugins.
  2. Claude Code reads that variable as turning the plugin pass off as well, unless `FORCE_AUTOUPDATE_PLUGINS=1` is also set (`plugins/loading`, `env-vars`). The declaration `init` writes sits below it: `autoUpdate` on a marketplace entry decides whether that marketplace is in the pass, not whether the pass runs.
  3. The harness asks for the pass and reads nothing about it. ADR-8 made the plugin update the only route a gate fix has, and the plugin's `SessionStart` hook, which runs with the session's process environment in hand, says nothing when the pass is off. The silence is what makes this row 1's class rather than a slow update.
  4. The fail-open half is 3 from the other side. A project migrated to 0.23.0 or later trusts the plugin to carry its gates, and nothing on the project's side reads the loaded version against what the project needs. On an install older than 0.23.0 there is no plugin hook to read anything, so only the project's documentation and `init`'s migration step can speak, and CI's `check-unreviewed-work.sh` is the one backstop.
- Acceptance criteria:
  - [ ] **AC1:** WHEN the plugin's `SessionStart` hook runs in a project with `.steering/` and the process environment has `DISABLE_AUTOUPDATER=1`, `DISABLE_UPDATES=1` or a non-empty `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC`, and `FORCE_AUTOUPDATE_PLUGINS` is not `1`, THE SYSTEM SHALL print one factual line on stdout, with the digest, naming the loaded plugin's version and saying that this session runs no plugin auto-update pass and what turns it on. WHEN none of the three is set, or `FORCE_AUTOUPDATE_PLUGINS=1` is, THE SYSTEM SHALL print no such line. Never on `Stop`, never in a project without `.steering/`, never where the digest stands down, and never on stderr.
  - [ ] **AC2:** `scripts/test-gates.sh` gains one case holding AC1's branches, and it fails on the merge-base's `hooks/plugin-gate.sh` for the right reason, no line printed, and passes after.
  - [ ] **AC3:** `hooks/templates/claude-code.settings.json` carries `"env": { "FORCE_AUTOUPDATE_PLUGINS": "1" }`, the declaration both READMEs quote carries it, and `scripts/check-readme-claims.py` compares it: with the key dropped from the template or from either README, the guard fails naming the file. Conditional on Q1 and on AC4's measurement finding that a settings `env` value reaches the pass.
  - [ ] **AC4:** `docs/verified.md` gains a section citing #274, directly before `## Still to verify`, recording this spec's measurements with their provenance and limits: a headless run from a desktop session's shell under each placement of `FORCE_AUTOUPDATE_PLUGINS=1`, and whether a pass ran in a session held open past the delay. Its `## Still to verify` item for #274 is restated to what remains after Q4: a real desktop session on a project whose settings carry the line, or ticked if T1 ran one.
  - [ ] **AC5:** every statement that a gate fix arrives by plugin update says when it does, in one sentence each: `docs/fidelity.md`'s **Gate delivery** row, `docs/layout.md`, `hooks/templates/README.md`, `skills/init/SKILL.md`'s Claude Code hook bullet, ADR-8 by a dated line, both READMEs' install paragraph and desktop-app row, and both READMEs' "then a new session or `/reload-plugins`" under **Updating**, which holds for the gates and not for a by-hand check (R1).
  - [ ] **AC6:** `skills/init/SKILL.md` and both READMEs say what the `env` line does, that a collaborator turns it off for themselves with the same key in `.claude/settings.local.json`, and that a machine whose install predates 0.23.0 runs no gate in a migrated project until its plugin updates, which the line brings at that machine's first desktop session in the project and the gates at its second.
  - [ ] **AC7:** every validator on `.steering/tech.md`'s `- Validators:` line exits 0 at the tip, `./scripts/test-gates.sh` reports the merge-base's count plus AC2's case, and `./scripts/check-version-bump.py <merge-base>` exits 0.
- Out of scope: the cloud-session gap (#261); a pass installing a newer version, which no run here can see while the install is at the latest release; the Antigravity half, which copies its gates; `/reload-plugins` and a resume not setting `GATE_SDD_PLUGIN_ROOT` (R1) and the checks' "unset" diagnosis, both row 11; a digest line that compares the loaded version with the marketplace, which needs a network read in a `SessionStart` hook, which this harness's gates do not do.

### Clarifications

Run 2026-10-10. The issue lists four directions and chooses none, and the backlog row says the first thing to measure is whether a settings `env` value reaches the pass. This session measured it before asking (the Design's measurement, and AC4), so the questions are what the measurement leaves. Each carries its recommended answer. The maintainer answered all four as recommended on 2026-10-10 and approved the spec.

- **Q1. Where does `FORCE_AUTOUPDATE_PLUGINS=1` go?** Recommended: **(a)** the template `init` renders into the project's `.claude/settings.json`, so it reaches everyone the declaration reaches, with the opt-out in `settings.local.json`. The declaration already says the project wants the plugin current, and the line is that intent made effective in the desktop app. The issue's regression risk is real and bounded: in that project's sessions the line forces the pass for every marketplace with auto-update on, which is what any terminal session on the same machine already does, and it reaches collaborators who did not choose it, as the declaration and the trust dialog in front of it already do. The others: **(b)** user settings, as a README instruction, which reaches only those who read it, which is this issue's shape, and makes AC1's line the whole remedy for everyone else; **(c)** nothing shipped. Answered as recommended, 2026-10-10.
- **Q2. Does the plugin's `SessionStart` say when the pass is off (AC1)?** Recommended: **yes**, one factual line, read from the process environment, no network. The alternatives are no line, which leaves "nothing tells them" standing for every machine the template has not reached, and a line comparing the loaded version with the marketplace, which is a `SessionStart` hook that reaches the network, which `.steering/tech.md` rules out for the gates. Answered as recommended, 2026-10-10.
- **Q3. The pre-0.23.0 fail-open: prose and Q1's convergence, or a project-side guard?** Recommended: **prose** (AC6). A project-side `Stop` entry is what ADR-8 took out, a guard in a JSON string is one nobody tests, and nothing on the project's side can read the plugin's version at turn end without the plugin. With Q1(a) a stale desktop-only machine converges in one session, and CI's unreviewed-work check already backstops the first. Answered as recommended, 2026-10-10.
- **Q4. Does the template change ship on the headless measurement, or after a real desktop session?** Recommended: **after a real desktop session**, as T1's second half. It costs one new session from the app in this checkout with the line in its gitignored `.claude/settings.local.json`, and the ledger then records a run rather than an inference from the documented precedence rule. If the maintainer would rather not, AC4 records the headless runs and the item stays open, restated. Answered as recommended, 2026-10-10.

## 2. Design (HOW)

- Fix approach, and why this rather than the narrower or wider fix: three layers, which is AGENTS.md's second idea applied to one defect. **The route is made to work where it was closed:** the template `init` renders gains the `env` line, so the update ADR-8 made the only route runs in the app for every project the declaration reaches (Q1). **The silence is made loud at the layer that cannot be talked out of it:** the plugin's `SessionStart` hook reads the process environment and says when the pass is off (Q2). **The claims are narrowed to what was run** (AC4, AC5), and the pre-0.23.0 case is stated where a migration reads it (Q3, AC6). The narrower fix is the README instruction alone, which this issue already shows reaching no one. The wider ones are a network comparison in the digest and a project-side guard, both rejected in the Clarifications.
- **The measurement**, run 2026-10-10 before this section was written, from this desktop session's shell at Claude Code 2.1.294, which carries `DISABLE_AUTOUPDATER=1` and `CLAUDE_CODE_ENTRYPOINT=claude-desktop`. Every run had its own plugin root through `CLAUDE_CODE_PLUGIN_CACHE_DIR`, so nothing of the machine's plugin state was read or moved, and `--setting-sources project,local` kept user settings out.
  - **F1, the check at startup.** Five headless `claude -p` runs with `--debug-file`. With the shell's environment and nothing else, twice, the second with the root already populated: `Plugin autoupdate: skipped (auto-updater disabled)`. With `--settings '{"env":{"FORCE_AUTOUPDATE_PLUGINS":"1"}}'`, with `FORCE_AUTOUPDATE_PLUGINS=1` in the process environment, and with `DISABLE_AUTOUPDATER` unset: no such line.
  - **F2, the pass itself.** Three sessions held open twelve minutes by an open stdin (`--input-format stream-json`), each declaring the marketplace with `"autoUpdate": true` and enabling the plugin through `--settings`, which cloned the marketplace into each root (`git clone … ref=default`, `Synced autoUpdate=true from settings for marketplace: gate-oriented-sdd`). First message at 00:41:31 UTC in all three. Control: skipped at startup, and nothing after. `FORCE_AUTOUPDATE_PLUGINS=1` in the process environment: `Plugin autoupdate: checking installed plugins` at 00:44:06. The same in `--settings` `env`: the same line at 00:45:25. So a settings `env` value reaches the pass, and AC3's condition holds. T4 records what the pass did after that line, from the final logs.
  - **Limits, which AC4's section states.** A headless process started from a desktop session's shell carries the app's variables but is not a session the app launched: the documented rule that a settings `env` value is ignored for a variable the launch environment already sets (`settings-reference`) was not exercised, and does not bite here because the app sets `DISABLE_AUTOUPDATER` and not `FORCE_AUTOUPDATE_PLUGINS`. `--settings` is the layer measured; the documentation applies `env` from user settings, `--settings` and managed settings at startup, and from project and local settings after trust, or at startup in `-p` mode (`settings-reference`). The project file is what the template writes, and T1's second half runs it in a real desktop session if Q4 holds. No root had an installed plugin for the pass to update, and no newer version existed, so delivery stays open, as the #256 section's item says.
- **The `env` line.** `hooks/templates/claude-code.settings.json` gains `"env": { "FORCE_AUTOUPDATE_PLUGINS": "1" }` after `enabledPlugins`. `scripts/check-readme-claims.py`'s `DECLARATION_KEYS` gains `"env"`, so the fence both READMEs quote must carry it, and the guard's existing per-key JSON comparison reads the nested object as written. The sentence after the fence, in both languages, says what the line does and names the opt-out: the same key set to `"0"` in `.claude/settings.local.json`, which outranks the project's file ("when more than one settings file sets a variable, the highest-precedence one applies", `settings-reference`; the opt-out itself is documented, not run). What the line does in a terminal session: nothing, since the pass is on there. In a session where the user set `DISABLE_UPDATES=1` themselves: it forces the plugin pass on, which `plugins/loading` says the variable does, and which the opt-out answers. In a cloud session: the pass finds no plugin installed (#261), so nothing. This repository's own `.claude/settings.json` carries no declaration and gains no line; it runs its hooks from source (ADR-6).
- **The digest line**, in `hooks/plugin-gate.sh`, step (3). On `SessionStart` the digest runs as a child rather than by `exec`, its exit status is kept, and after it the wrapper prints the line when the pass is off: `- This session runs no plugin auto-update pass: <the variables set, as NAME=value, joined by " and "> and FORCE_AUTOUPDATE_PLUGINS is not 1. gate-sdd stays at the loaded <version> until a by-hand update (claude plugin marketplace update gate-oriented-sdd, then claude plugin update gate-sdd@gate-oriented-sdd) or until a settings file's env sets FORCE_AUTOUPDATE_PLUGINS=1 and a new session starts.` A variable counts as set in its documented form: `DISABLE_AUTOUPDATER=1`, `DISABLE_UPDATES=1`, `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC` non-empty (`env-vars`); the comment says so, and that other spellings are not read. The version is `"version"` from `.claude-plugin/plugin.json` beside `hooks/`, the manifest Claude Code loads, or `unknown` when it cannot be read; the plugin name is written, as the gate names are. The line is a statement, as the digest's header comment requires. After the digest rather than before, because the digest's heading is the first line a session reads and the fact belongs under it. The `Stop` path is unchanged, `exec` included. Steps (1) and (2) run first, so the line never prints in a project without `.steering/` or where the digest stands down (AC1). The process environment is the right source: a hook is a child of the session's process, U2 read the variables from those processes with `ps eww`, and this session's Bash prints them.
- **The case**, 221 in `scripts/test-gates.sh`, after case 220 and its helpers. The fixture is `pg_repo` plus a `.claude-plugin/plugin.json` under `plugin/` with `"version": "9.9.9"`. Each branch controls the four variables itself, in a subshell that unsets all four and then sets what the branch needs, because the suite may run in a desktop session whose shell carries `DISABLE_AUTOUPDATER=1`. Branches: (a) `DISABLE_AUTOUPDATER=1` alone: exit 0, `## Repo facts` on stdout, the line last on stdout naming `DISABLE_AUTOUPDATER=1` and `9.9.9`, nothing on stderr; (b) with `FORCE_AUTOUPDATE_PLUGINS=1` as well: no line; (c) none of the four: no line; (d) `DISABLE_UPDATES=1`: the line names it; (e) `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1`: the line names it; (f) both `Stop` gates under (a)'s environment: the line nowhere on stdout; (g) no `.steering/` under (a): silent; (h) the digest standing down under (a): silent; (i) no manifest under (a): the line with `unknown`. Red-capability by sequence: on the merge-base's wrapper (a), (d), (e) and (i) fail, no line printed. The existing digest cases are unaffected: 220(e) compares two wrapper runs under one environment, and the stand-down cases assert an empty stdout, which the line does not reach.
- **The statements** (AC5, AC6), one sentence each, in T3: `docs/fidelity.md`'s **Gate delivery** row says the desktop app's pass needs the line; `docs/layout.md`'s paragraph the same; `hooks/templates/README.md`'s Claude Code bullet names the line as what the template carries; `skills/init/SKILL.md`'s Claude Code bullet names the line beside the declaration, keeps every pinned phrase as it is, and its migration step 1 adds the line with the declaration and gains the pre-0.23.0 sentence; ADR-8 gains a dated line under **Consequences**. `README.md` and `README.ja.md`: the paragraph after the fence (T2), the `"autoUpdate": true` paragraph's desktop sentence, the desktop-app row's first cell narrowed to a project without the line and a row added for a machine whose install predates 0.23.0, and under **Updating** the `/reload-plugins` clause, which says the reload loads the new gates and did not set `GATE_SDD_PLUGIN_ROOT` (R1). The Japanese passages are drafts for the maintainer's reading, with the same claims as the English.
- **`docs/verified.md`** (AC4, T4): a section headed `## FORCE_AUTOUPDATE_PLUGINS=1, and from where it reaches the pass (#274)`, directly before `## Still to verify`, with a provenance paragraph, F1, F2, F3 if run, and **What this run does not support** from the limits above. **Last updated** to 2026-10-10; the Claude Code version row gains 2.1.294 for this section. The `## Still to verify` item citing #274 is ticked if F3 ran, and otherwise restated to the desktop session alone. No other `- [ ]` changes, and the #256 section's open item on delivery stays as written.
- Affected files: `hooks/plugin-gate.sh`, `hooks/templates/claude-code.settings.json`, `scripts/test-gates.sh`, `scripts/check-readme-claims.py`, `README.md`, `README.ja.md`, `docs/verified.md`, `docs/fidelity.md`, `docs/layout.md`, `hooks/templates/README.md`, `skills/init/SKILL.md`, `docs/decisions/ADR-8-the-claude-code-gates-ship-from-the-plugin.md`. Two shipped paths change, so the version moves to 0.25.0 as a step of `implement`: a hook and a template are a flow change, minor.
- **Blast radius:** `hooks/plugin-gate.sh` runs on every `SessionStart` of every Claude Code project with `.steering/`; the change is one more line of stdout when the pass is off and none otherwise, and the `Stop` path is byte-identical. The template reaches every project `init` writes from 0.25.0; a project written earlier has no line until `init` runs again or someone adds it, and the README's **Updating** says so. `scripts/check-readme-claims.py` gains one tuple entry, and the guard's other claims are untouched. The suite gains one case, and `test-gates.sh` run from a desktop session now exercises the line in every digest case through the environment it inherits, which is why 221 controls the variables itself.
- Why this cannot recur: the README guard holds the quoted declaration to the template, so the line cannot leave one without the other; case 221 holds the hook's line to its branches; and the ledger records a run, so the next claim that the pass runs in the app has one behind it. What it does not make impossible: the app changing what it sets, or Claude Code changing what `env` reaches. Either would show as AC1's line appearing again on a machine whose project carries the template's line, which is loud, where the defect this spec fixes was silent. A `check-skill-contracts.py` pin for `init`'s sentence about the line was considered and not added: the behaviour travels with the template, which the README guard already holds, and the pin would protect an explanation.
