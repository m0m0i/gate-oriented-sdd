# Spec: an earlier run's pass, written after a later run failed, skips the validators on a red tree
- Slug: 331-a-late-pass-does-not-outlive-a-later-failure   Issue: 331   Type: bug   Status: approved
- Author: m0m0i   Date: 2026-10-21

## 1. Requirements (WHAT / WHY)
- Reproduction: two runs of `hooks/quality-gate.sh` overlap in one worktree. Measured on `main` at `8c7c5e1` as a `scripts/test-gates.sh` case placed after `qgp_repo`, sequenced by marker files so the interleaving is the same on every run (#331 quotes it in full); the suite went 352 passed, 1 failed:
  1. Run A starts on a green tree, takes its fingerprint, and holds in its validator.
  2. `bad.cfg`, outside `- Source globs:`, turns the tree red.
  3. Run B removes the pass record, runs the validators, fails, and blocks.
  4. Run A finishes green and records the fingerprint it took before B started.
  5. The next turn end, `bad.cfg` still present, matches that fingerprint and exits 0 with `{}`, running no validator (`runs=2`, want 3).
- Expected: #297's AC3 holds with two runs at once. Once a turn end's validators have failed, every later turn end runs them until a run passes, and a run that started before that failure is not "a run" that ends it: its pass is evidence about the tree as it was before the failure was seen. Under `- Owns: gates never fail open` (`.steering/product.md`), a gate that exits 0 when it should have blocked is at least HIGH.
- Actual: the earlier run's pass is recorded after the later run's failure, and the next turn end skips the validators on a red tree.
- Impact: every project where two gate runs can overlap in one worktree. On Claude Code, two sessions in one checkout — this repository's own way of working. On Antigravity, the workspace `Stop` gates also run in the read-only reviewer subagent's turn while the parent's turn ends (#329), so `implement`'s own path overlaps two runs. It needs no damage. It needs the two runs to disagree: an input outside the globs that changed between their starts, as above, or two suites in one worktree interfering through a shared cache, port or database.
- **Root cause:** the pass record is one value per worktree (`git rev-parse --git-path gate-sdd/quality-pass`), and the run that writes it is the one that finishes last, not the one that started last. Each run removes the record before its first validator (`hooks/quality-gate.sh:442`) and, when every validator passed, writes the fingerprint it took before they started, through `mktemp` and `mv` (`:482-488`). Those two steps protect a run against itself: a failure leaves no pass, and an edit made during the run is not recorded as passed. Nothing relates one run's write to another run's start or failure, and the skip at `:422-427` trusts any record whose fingerprint matches. Each run has its own `mktemp` run directory (`:161-169`), and there is no lock and no ordering. The fingerprint cannot tell the two runs apart, because both took it over the same source: what turned the tree red was outside the globs, or was not a file change at all.
- Acceptance criteria:
  - [ ] **AC1:** WHEN run A starts, run B starts after it in the same worktree and fails, and A then passes, THE SYSTEM SHALL run the validators at the next turn end and block on the red tree. This is the reproduction above: `exit=2` and three runs. The same holds for any record whose writer is no longer the latest run to start or fail, including a record left by a run killed after writing it.
  - [ ] **AC2:** WHEN a run fails, THE SYSTEM SHALL skip on no pass recorded by a run that started before that failure finished, whichever of the two finishes first (Q1).
  - [ ] **AC3:** WHEN a run cannot establish whether it is still the latest, because a step it needs to tell fails or the token path is not a regular file, THE SYSTEM SHALL record no pass, leave nothing inside a path that is not a regular file, and say so on stderr. The message keeps the words "could not be recorded" (`:486`) and names the step. The run's own verdict is unchanged: validators that passed still pass its turn, and the next turn end pays for a run, never for a pass.
  - [ ] **AC4:** WHEN only one run is in flight, THE SYSTEM SHALL behave as on `main`: every #297 case (239–258) and every #304 quality-gate case passes. The one fixture change is case 298's `mv` shim (`scripts/test-gates.sh:3517`), which hung on every `mv` and now hangs only on the record's, since the start token adds an `mv` before the first validator. 298 stays red under "the parent leaves the record when it builds the block".
  - [ ] **AC5:** the tests: `scripts/test-gates.sh` cases for AC1 (the reproduction, and a record whose writer is not the current token), AC2 (both orders of finishing) and AC3, placed after the fixture each uses. Each fails before its task: on `main`, or after the task before it.
  - [ ] **AC6:** every statement of the record's semantics stays true — `docs/DESIGN.md:32`, `docs/layout.md:102`, and the comments in `hooks/quality-gate.sh` that describe the record — and every command on the `- Validators:` line exits 0.
- Out of scope:
  - The review gate. It keeps no pass record; it reads the receipt.
  - #329: whether Antigravity should run the workspace gates in a reviewer subagent's turn at all. This spec makes the overlap safe, not absent.
  - Two runs in two different worktrees. The record is per worktree (#297's AC8), so they cannot write each other's.

### Clarifications
Asked and answered 2026-10-21.

- **Q1 — the reverse ordering: run B starts after run A and passes, then A fails. Does B's pass stand?** **A:** no, any failure ends every earlier-started pass (AC2). When two runs disagree about the same source the gate cannot tell which is right, and it blocks; the cost is one extra run in that interleaving. "Later start wins" was rejected because it keeps a pass past a failure that finished after it.

Decided rather than asked, as design calls: a run never waits for another (Design); a run counts as started when it gets past the skip and is about to run the validators, whether or not a record exists, so a turn end that skips starts nothing; a run cut off before it finishes leaves its start standing, which withholds every earlier run's pass and never grants one.

**Revised 2026-10-21, before approval, from a four-lens spec review** (fail-open, portability, tests, conventions; every HIGH re-checked by an independent verifier). The first Design checked the token after writing the record, and that held for the state left at the end but not for a reader in between: a third run's skip, or a SIGKILL between the write and the check, trusted a record still unverified. It also cleared only the record on a failure, so a run already in flight that started earlier could record after the failure finished. Both were confirmed HIGH. The check now happens where the record is read, and a failure is an ordering event like a start. The review also found that the token's `mv` hangs case 298's shim (AC4), that `mv` onto a directory succeeds silently on BSD and GNU alike (AC3), that cases 247 and 258 depend on the "could not be recorded" wording (AC3), and that `docs/layout.md` and Antigravity's copied hooks were missing from the blast radius.

**Amended 2026-10-21, during T1, from the T1 review** (confirmed by an independent verifier; agreed by the author). Step 3 as approved wrote the failure to the token only after the validator loop, which the parent's timeout and signal blocks never reach: a run that failed a validator and was then cut off left the token naming a later-started run, whose pass then stood on a tree the earlier run saw red. That breaks AC2. Step 3 now writes the token at the first failing validator, the parent's `qg_block` writes one on every block it builds, and T2 gains a case for the cut-off run. The same review found the Blast radius's "mixed versions are safe both ways" true of the record's format only, not of the race; it now says which. No acceptance criterion changed.

**Amended again 2026-10-21, during T2, from the T2 review** (confirmed by an independent verifier, which reproduced it; agreed by the author). Step 3 as amended wrote the token only at a run's first failing validator, so a run that started between that failure and a later one recorded its pass after the later one: a red tree skipped. Step 3 now writes at every failing validator. T2 names five cases: 345, which pins the parent's half, and 346, this interleaving, join the three agreed. No acceptance criterion changed.

## 2. Design (HOW)
- Fix approach: **order the runs, do not serialise them, and check the order where the record is read.** A per-worktree token beside the record, `${qg_record%/*}/quality-run`, holds the id of the latest **ordering event**: a run's start, or a run's failure. The record gains a second line, its writer's id, and is honoured only while the token still holds that id. The id is the run directory's name and the child's pid, `${run##*/}.$$`: `mktemp` makes the name unique among live runs, the pid separates a reuse after a removed directory, and neither contains a space. Every write of the token goes through `mktemp` in the record's directory and `mv`, so a reader never sees half a value, and only after checking that the target is absent or a regular file, because `mv` onto a directory moves the file into it and reports success. The child's `EXIT` trap removes a pending `quality-run.*` or `quality-pass.*` temp file it made. The child changes in four places:
  1. **Start.** A run that gets past the skip writes its id to the token before it removes the record at `:442`. If the write fails, it removes the token (`rm -f`, only if the path is a regular file), names the failed step on stderr, and carries on with the validators; it cannot record a pass, because the token does not hold its id. A token that cannot be written or removed is named too, and every earlier run's record is then honoured only if the token still names its writer, which the failed write did not change: the same residual as a record that cannot be removed (`:442-444`), and named the same way.
  2. **Pass.** Where it writes the record (`:482-488`), the run reads the token. Only if it holds this run's id does it write the record, as `<fp>` then `<id>`, through `mktemp` and `mv`. Otherwise, or if the read fails, it records nothing and says so in the shape of `:486`, naming the reason. This read saves a stale run from overwriting a newer pass; correctness does not depend on it, because of step 4.
  3. **Fail.** At every failing validator, before the next one starts, a run writes a fresh id, `<id>.failed`, to the token, then removes the record, and only then runs the validators left and blocks. Writing the token first means any run that started earlier, whether it is still running or already recorded, now names a writer that is not the latest. Writing it at each failure, not after the loop, means a run cut off or signalled after a validator failed has already ordered itself; writing it at every failure, not only the first, means a run that started between two of them is ordered by the later one. The parent's `qg_block` (`:141-151`) also writes a fresh value ending in `.failed` before it removes the record, so every block the parent builds, the timeout and signal blocks included, is an ordering event too. No writer's id ends in `.failed`, and a token write can only withhold a pass, so writing one on every parent block opens nothing. If the token cannot be written, the run removes it; if the record cannot be removed either, the block message carries `qg_block`'s sentence that the next turn end may skip on it (`:146-149`).
  4. **Skip.** At `:422-427` a record is honoured only when its first line equals `$fp` and its second line equals the token's current content. A missing, unreadable or non-regular token, a record without a second line, and a mismatch all run the validators. A mismatch is ordinary (another run started or failed since) and is said once on stderr; a step that failed is named as `qg_step` already is (`:436`).
- Why this rather than a lock: a lock makes the second run wait, and the wait counts against the deadline #304 holds each gate to. POSIX `sh` has no `flock`, so a `mkdir` lock would also need stale-lock recovery for a run killed while holding it, and recovery that guesses wrong is either a false block or a fail-open. Ordering needs no wait and no recovery: a run that dies mid-way leaves a token that only ever withholds a pass.
- Why not narrower: removing the record when a run fails fixes neither order on its own. In the reproduction B finishes before A, so B's removal comes before A's write; and a run already in flight can write after any removal. Re-checking the fingerprint does not help, because both runs took the same one. A check after the write, the first Design, leaves the record trusted in between.
- Affected files: `hooks/quality-gate.sh` (the child's start, pass, fail and skip paths, its `EXIT` trap, the parent's `qg_block`, and the comments describing the record); `scripts/test-gates.sh` (the cases in AC5, and case 298's shim); `docs/DESIGN.md:32` and `docs/layout.md:102` (the record's semantics).
- **Blast radius:** every run that gets past the skip takes one more `mktemp` and `mv` at its start, and every skip one more read, all in the git directory, none in the work tree. #297's AC8 still holds: the gate writes no git object and leaves the real index alone. The record's format is safe across versions both ways: a record a pre-fix run wrote has no second line, so a fixed run does not skip on it and runs once; a pre-fix run compares the whole record with its fingerprint, so a two-line record never matches it and it runs. The race is not: a pre-fix run writes no token and checks none, so a worktree where fixed and pre-fix copies of the gate both run keeps the fail-open in every interleaving that involves a pre-fix run, until every copy is updated. Claude Code projects get the fix by plugin update, since the plugin's `Stop` hook runs this script (`hooks/plugin-gate.sh`). Antigravity projects run copies under `.agents/hooks/`, so they get it only by re-running `init`; until then #329's overlap stays a fail-open there, and so does any worktree where a Claude Code session on the updated plugin and an Antigravity session on old copies both end turns. The release note says both. The review gate does not share the record.
- Why this cannot recur: the record can no longer outlive its writer's turn as the latest run. The token is the one place that knows which run that is, the skip path consults it, and AC1's stale-writer case goes red if a future change skips on a record without it.
