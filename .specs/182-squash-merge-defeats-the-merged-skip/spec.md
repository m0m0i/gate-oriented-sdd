# Spec: the merged-branch skip never fires where the repository squash-merges

- Slug: 182-squash-merge-defeats-the-merged-skip   Issue: 182   Type: bug   Status: approved
- Author: m0m0i   Date: 2026-09-20

## 1. Requirements (WHAT / WHY)

- Reproduction: two forms, one mechanism.
  1. **Hermetic** — case 8's fixture with the merge style swapped. Build `scripts/test-gates.sh:136-138` with `git merge --squash 9-feature && git commit` in place of `git merge -q 9-feature`, stand back on `9-feature`, and run `hooks/review-gate.sh`. The branch has shipped, its tasks are ticked, no receipt was ever written — the state `hooks/review-gate.sh:29-30` exists to stay quiet about — and the gate blocks. Case 82 (`:350-352`) is the same substitution one branch over, scanned from `main`.
  2. **Live in this tree** — `79-backlog-drifts-from-the-tracker` merged as PR #183 at 12:52Z on 2026-09-20. `git merge-base --is-ancestor 79-backlog-drifts-from-the-tracker origin/main; echo $?` answers `1`, and `git branch --merged main` lists only `main`. The issue counted thirteen such branches when it was filed; the count is incidental and the ratio is not — no branch with a merged pull request has ever been an ancestor of `main` in this repository.
- Expected: `hooks/review-gate.sh:29-30` states the contract in its own words — *"Already-merged work has nothing left to review. Without this, every historical feature branch trips the gate the moment the harness is installed."* The skips at `:63` (the branch HEAD is on) and `:111` (every other branch) SHALL fire for work that has reached the base, whatever merge style put it there. `scripts/test-gates.sh` case 8 asserts that for the current branch and case 82 for a parked one.
- Actual: a squash merge writes a new commit on the base whose tree is the merged result and whose only parent is the base's previous tip. Nothing links it to the branch, so the branch tip is not in the base's history, `git merge-base --is-ancestor` is false by construction, and it will stay false forever. Neither skip ever fires in such a repository. There is no diagnostic either: `$base` resolves normally, so the no-base note at `:126-128` — the one path that admits the gate cannot tell what has shipped — is for a different condition and stays silent. Every shipped-but-undeleted spec branch falls through to `gate_spec_review_state` on every turn, permanently. **Both test cases pass, and both build their fixture with a real `git merge -q`,** so the suite exercises a merge style this project does not use and reports the protection as working.
- Impact: every project that squash-merges and does not delete its local branches, which is GitHub's common default and this repository's own convention — `docs/CONTRACT.md:80` records that `main`'s subjects are squash-merge subjects, and `.claude/settings.local.json:4` allows only `gh pr merge --squash`. The direction is what makes it urgent rather than tidy: this fails **closed**, permanently, from every branch at once. `- Owns: gates never fail open` is not the property at risk — CAP-7, *a gate people leave switched on*, is, and `hooks/review-gate.sh:12-14` names that cost itself. It has been invisible here only because a second mechanism covered for it: each merged branch carried a CLEAN receipt whose `reviewed_sha` sat behind its tip, and the trailing commits touched nothing matching `- Source globs:`. Verified on the one branch left — receipt at `3bfeacc`, tip at `b14636d`, three commits between them (worklog, release, backlog prose), and `git diff --name-only 3bfeacc..b14636d -- <globs>` empty. That silence has no second line, and three ordinary events remove it, each producing a permanent block on every turn from everywhere: a post-review rebase orphans `reviewed_sha`, which since #26 returns `unresolved-sha` and blocks (correctly for a branch being worked on, unclearably for one that shipped six weeks ago); `git gc` prunes an orphaned sha with the same result, from housekeeping nobody ran deliberately (`.work_logs/2026-09-20.md:181`); and widening `- Source globs:` recomputes every old branch as stale at once, so one steering edit blocks on all of them. Before #26 widened the scan the blast radius was the branch you were standing on; since #26 it is the repository.
- **Root cause:** the skip's evidence for *this work shipped* is commit ancestry, and ancestry answers a different question — **was this commit joined into the base's history**, not **did this work reach the base**. Under a merge commit or a fast-forward the two coincide, which is why the check has read as correct for its whole life. A squash merge replays the branch's tree as a new commit with no parent link, so the two come apart and never rejoin: this is not a test that fails sometimes, it is a test being asked a question that can no longer have a true answer. The second half of the cause is why nobody saw it — both fixtures froze the one merge style in which the two questions coincide, so the suite could not report the difference, and it reported a pass instead.
- Acceptance criteria:
  - [ ] **AC1:** WHEN a spec branch's work has reached the base by a squash merge, and the branch's tip carries nothing beyond what reached the base, THE SYSTEM SHALL stay silent about that branch — both while HEAD is on it and while it is scanned from elsewhere.
  - [ ] **AC2:** WHEN such a branch has carried on past the merge and holds reviewable work the base does not, THE SYSTEM SHALL NOT skip it, and SHALL report it exactly as it reports any other branch holding finished, unreviewed work. This is the fail-open the fix must not open: a slug reaching the base is a fact about the spec, not about the branch, and treating the first as the second is #26's defect returning through the door built to close its side effects.
  - [ ] **AC3:** AC1's silence SHALL continue to hold where the work reached the base by a merge commit or a fast-forward. The skip widens; it does not move.
  - [ ] **AC4:** WHEN any input the skip depends on cannot be resolved — no base, no copy of the slug in the base's tree, or no commit on the base that carries it — the skip SHALL NOT fire, and the note at `hooks/review-gate.sh:126-128` SHALL still be printed in the no-base case. A repository that cannot say what has shipped SHALL NOT be made silent by this change, and a shallow clone SHALL NOT be quieter than a full one. (G-1, `- Owns: gates never fail open`.)
  - [ ] **AC5:** every behaviour in AC1–AC4 SHALL have a case in `scripts/test-gates.sh` that is **red-capable** — it fails before the change, or, where the implementation already carries the path, under a **named mutation** that removes the specific refusal the case asserts, with the mutation and what it flipped recorded per case. Each case SHALL assert on the exit code **and** on the blocking message, and no pre-existing case SHALL change verdict. Cases 8 and 82 SHALL NOT remain the only evidence for either skip: a fixture built with a merge style the project does not use is how this defect survived, so that is the part the suite has to stop doing.
  - [ ] **AC6:** the comment at `hooks/review-gate.sh:29-30` SHALL be corrected to describe the case the skip actually covers. Verified today: a historical branch with no spec of its own is already silent whatever the merge style, because an absent `.specs/<branch>/spec.md` returns empty from `gate_spec_review_state` before ancestry is consulted — so *"every historical feature branch trips the gate the moment the harness is installed"* names a case that cannot occur, while the case that can — a branch that shipped **with** a spec — goes unnamed. A comment that justifies a skip by a scenario the code no longer faces is how the next reader re-derives this from scratch.
- Out of scope: **deleting merged local branches** — it clears the symptom, and `gh pr merge --squash --delete-branch` is already the allowed path here, but the hook's stated purpose at `:29-30` is precisely the branch that still exists when the harness is installed, so a fix that requires the branch to be gone fixes nothing. **Asking the tracker whether a pull request merged** — a `Stop` hook must not touch the network, for the reason `.steering/tech.md` records against `check-backlog-tracker.py`; it applies here unchanged. **Running `archive`** — sweeping shipped specs into `.specs/_archive/` is a sweep run on request, not a step in the flow, so a fix with a sweep as its precondition is a fix with a manual precondition. Whether `_archive/` counts as *evidence* is a question for `clarify`; running it is not part of this. **#177 and #176** — the current branch read from the working tree, and the missing default arm in `check_current_branch`'s `case`. Same function, row 3, different defect. **`assets/check-unreviewed-work.sh`** — checked, and it carries no ancestry skip of its own, because it asks about a pull request's head, which by definition has not merged.

### Clarifications

Asked and answered 2026-09-20, before any Design existed. Two questions, both about the shape rather than the wording, and both carrying a recommendation that had already been tested against a fixture rather than reasoned about — which is why there were two and not five. The decisions taken **without** asking are recorded in Design, where their reasoning belongs.

1. **How does the gate decide a branch's work reached the base?** — *Answered: evidence plus a footprint test.* Shipped is `.specs/<slug>/spec.md` or `.specs/_archive/<slug>/spec.md` present in the base's tree; *nothing further* is the branch's own source footprint being unchanged against the first commit on the base that carries that slug. Three candidates were built and driven against a fixture where the base moves on twice — once at an unrelated path, once at the very file the branch touched — and only this one answers both directions: silent for the shipped-and-idle branch, blocking for the branch that carried on past its merge. Rejected: **evidence alone** (one git call, no anchor, and the fail-open the issue predicted — a branch that merged and kept committing goes silent locally, which is #26's defect arriving through the door built to close its side effects; CI would still catch it at the next pull request, but the local gate is the thing this repository exists to make trustworthy), and **comparing the branch against the base's tree** over `- Source globs:` (simplest content test, and it decays — every later commit to `main` touching any path the branch touched turns the skip back off, so in this repository it would stop firing within a week and the permanent block would return wearing a new mechanism).
2. **Does the skip sit before the review-state check, silencing a shipped branch whose review evidence is missing, orphaned, stale or not CLEAN?** — *Answered: yes, where both call sites already put it.* The four states this silences are exactly the permanent blocks the issue is about — the install-time missing receipt, the rebase-orphaned sha, the sha `git gc` pruned, and the widened `- Source globs:` — and all four sit on work the gate cannot unship. Rejected: **skip except on a non-CLEAN verdict** (shipped work that never passed review is worth saying out loud, and the argument is real, but it splits the skip and leaves a state the scan must still reach, for a report whose only available remedy is to delete a branch or rewrite a shipped receipt), and **skip only on a CLEAN receipt** (narrowest, and it abandons the case `hooks/review-gate.sh:29-30` claims the skip exists for).

## 2. Design (HOW)

- **Fix approach, and why this rather than the narrower or wider fix.** One new question in `hooks/gate-lib.sh` — `gate_work_reached_base <slug> <tip> <base>` — called from both existing skip sites in `hooks/review-gate.sh`, as a second arm beside the ancestry test rather than in place of it. It answers in two steps, cheap first:
  1. **Did this spec reach the base?** `git cat-file -e "$base:.specs/$slug/spec.md"` or the same under `.specs/_archive/`. One call, and it prunes hard: a branch whose spec is not in the base pays for nothing below. Either location counts, and neither alone is enough — `_archive/` is timely only after a sweep that `skills/archive/SKILL.md` runs on request, and `.specs/` empties when that sweep does run, so a skip reading one location goes wrong in whichever state it does not cover.
  2. **Has the branch anything further?** `anchor=$(git rev-list --reverse "$base" -- .specs/$slug/spec.md .specs/_archive/$slug/spec.md | head -1)` — the **first** commit on the base carrying the slug, which in this flow is the squash commit, because the spec is the branch's first commit and reaches the base only when the branch does. First rather than last, so a later `git mv` into `_archive/` does not move the anchor forward onto work the branch never had. Then the footprint: `foot=$(git diff --name-only "$(git merge-base "$base" "$tip")" "$tip" -- $globs)` is what the branch touched, and `git diff --quiet "$anchor" "$tip" -- $foot` is whether it still matches what shipped. Empty means shipped and idle.
  The **narrower** fix — evidence alone — and the **wider** one — comparing whole trees — were both built and driven against a fixture before being rejected; clarification 1 records what each cost. Scoping step 2 to the branch's own footprint rather than to all of `- Source globs:` is what makes the anchor survive a moving base: the anchor's tree carries the branch's content at exactly those paths, and whatever else landed on the base between the branch's fork and its squash is at other paths and therefore not compared.
- **Ancestry is kept, as the first arm.** It is exact when it fires and costs one call. _Amended during T2, because the original reason was weaker than the measured one:_ the two arms turn out to overlap on every shape the suite can build — under the mutation that drops ancestry, the merge-commit case stays green, because the evidence arm answers it too. Ancestry's one unique contribution is a branch that merged and whose spec was then **deleted** from the base rather than swept into `_archive/`: the slug is in neither location, the evidence arm correctly refuses to read anything, and only ancestry carries it. That is case 138, and it is the answer to the question #182 left open about whether the ancestry check survives a content check. It does, for one case, and the case is now pinned rather than assumed.
- **Fail closed at every step.** An absent base, an absent slug, an unresolvable anchor, or a `git` that errors all leave the skip unfired and the branch gated exactly as it is today. That is the direction `- Owns: gates never fail open` requires, and it is also the direction that degrades to the status quo rather than to silence — the change can make the gate quieter only where it has positive evidence, never where it lacks it. AC4.
- **Affected files:** `hooks/gate-lib.sh` (the new question), `hooks/review-gate.sh` (both call sites, and the comment AC6 corrects), `scripts/test-gates.sh` (new cases; 8 and 82 kept).
- **Blast radius.** `gate_spec_review_state` is untouched — the skip sits before it, so no state, message or exit code changes for any branch the skip does not fire on. `assets/check-unreviewed-work.sh` sources the same library and is unaffected: it carries no ancestry skip, because it asks about a pull request's head, which by definition has not merged. `hooks/quality-gate.sh` does not call either function. What does change for consumers: `hooks/review-gate.sh` ships, so every install gets this at upgrade — a merge-commit project sees no behaviour change at all (AC3), and a squash-merging one sees branches it was blocking on go quiet, which is the point. The per-turn cost is bounded by step 1: the scan already runs `git for-each-ref` plus a `rev-parse` and a `merge-base` per branch, and only branches that pass the one-call evidence test add a `rev-list` and two `diff`s. A gate that takes seconds is a gate people switch off, which is the same CAP-7 this bug threatens from the other side.
- **Why this cannot recur.** Not by a new guard — the class here is *a fixture that encodes an assumption the project does not hold*, and nothing mechanical detects that in general; claiming otherwise would be the fail-open this repository is about. What the change does buy is that the assumption can no longer be silent: both merge styles are covered for both call sites, so the next person who narrows the skip breaks a case whichever style they had in mind, and the two-arm structure makes the ancestry assumption visible in the code rather than only in a fixture. The one definition in `gate-lib.sh` with two callers is the #14 and #23 pattern applied before a copy exists rather than after one disagrees.
