# Spec: init installs a reference rulebook over a project whose CONTRACT.md cites rules it does not carry
- Slug: 84-init-keeps-the-project-rulebook   Issue: 84   Type: bug   Status: approved
- Author: m0m0i   Date: 2026-10-12

## 1. Requirements (WHAT / WHY)
- Reproduction: a project has a `<docs>/CONTRACT.md` whose Rules table has Judgment rows citing ids compiled into its own reviewer's rulebook — fifteen on #76's target. Its agents directory is either absent (the stripped path) or present and being upgraded. Run `init`.
- Expected: the installed reviewer carries the rules the contract cites, or `init` says plainly which it does not and how to get them back. The issue's own Fix, and the Rules line *"If the project already has a harness from an earlier version, diff and upgrade rather than reinstalling."*
- Actual: step 3's reviewer bullet has one path — copy the closest reference reviewer and its reference rulebook — and it carries none of the project's ids. After the install the contract points at rules the reviewer does not have, and `check-locks.py --update` reports the reference lock matching the reference rules, which is true and beside the point. Observed 2026-09-05 on #76 (`.specs/_archive/76-run-init-on-a-scratch-clone/observations.md`, AC6) on the stripped path; the upgrade path has not been run.
- Impact: every project that ran `contract` and then re-runs `init`, which is how consumers take every fix that does not ship as a plugin update (`docs/BACKLOG.md` row 1). The reviewer is the judgment layer: a rulebook replaced silently means every later review cites the wrong rules and passes what the project's own contract forbids, with every guard green.
- **Root cause:** step 1's inventory names `.claude/` and `.agents/` as directories, never the reviewer inside them or the contract its rulebook answers to, so nothing `init` reads tells it the rulebook is the project's. Step 3's reviewer bullet then knows only the fresh-install case. The one sentence that keeps an adapted reviewer — migration step 2's *"never the reviewer itself, which the project adapted"* — sits inside the 0.23.0 migration and reaches no other upgrade. And nothing mechanical compares the contract's Judgment ids with the rulebook — `docs/CONTRACT.md` says so of this repository too — so the disagreement `init` creates is one no guard reports.
- Acceptance criteria:
  - [ ] **AC1:** step 1's table names `<docs>/CONTRACT.md` and the reviewer `- Reviewer:` names, with its rulebook and lock, among what is already installed.
  - [ ] **AC2:** WHEN the project's agents directory already holds the reviewer `- Reviewer:` names, step 3 keeps that reviewer, its `rules/` and its `rules-lock.json` — copying no reference reviewer or rulebook over them — compares only the plugin-owned files beside them (the shared reviewer contract, `check-locks.py`) and copies what differs, then re-pins with `check-locks.py --update`, saying so when the rulebook has no lock to re-pin (#19).
  - [ ] **AC3:** WHEN that reviewer is gone and `<docs>/CONTRACT.md` still has Judgment rows — the stripped path — step 3 first looks for the removed rulebook in git history and offers to restore it, then re-pins. Only when history holds none does it install a reference reviewer, name each Judgment id the reference does not carry, say those rows have no enforcer, and run or point at `contract` to recompile them before step 4 arms the gate.
  - [ ] **AC4:** WHEN `<docs>/CONTRACT.md` has a Judgment row whose id is not defined in a rulebook of the reviewer `- Reviewer:` names, `assets/check-locks.py` exits 1 naming the id, the contract and each rulebook directory that lacks it. Defined means a heading or bolded list item that opens with the id — a mention in prose does not count, and `G-10` does not define `G-1`. WHEN no rulebook directory for that reviewer exists, it fails naming the ids. WHEN the contract is absent, or has no Judgment rows, the lock half alone decides the exit. WHEN `- Docs:` names another repository, the lock half decides the exit and the output says the contract was not checked.
  - [ ] **AC5:** the regression tests — `scripts/test-gates.sh` cases for each branch of AC4, the passing control first, each failing before the change; and `scripts/check-skill-contracts.py` pins AC2's and AC3's sentences in `skills/init/SKILL.md`, failing on the tree before the edit.
  - [ ] **AC6:** every place that says nothing checks the contract against the rulebook — `docs/CONTRACT.md`'s preamble and its `M-8` row, `.steering/tech.md`'s `## Where the contract lives`, `AGENTS.md`'s validator comment — says what `check-locks.py` now checks, and what it still does not: rule text and severity.
  - [ ] **AC7:** the upgrade path is run on a scratch clone of #76's target, and what it kept, refreshed, re-pinned and reported is recorded in `observations.md` beside this spec, with no identifier from the target, by #76's rule.
  - [ ] **AC8:** every command on the `- Validators:` line exits 0.
- Out of scope: `contract` meeting a rulebook that already exists (#70, the same case one skill over); `check-locks.py --update` creating a lock (#19); duplicate or missing ids within `docs/CONTRACT.md`'s own tables (#116); a severity or wording disagreement between a contract row and its rule; `reviewer-contract.md` naming a guard that is not shipped (#188, #227).

## 2. Design (HOW)
- Fix approach, and why this rather than the narrower or wider fix: two halves. **The guard:** `check-locks.py` reads `- Docs:` (default `docs/`) and `- Reviewer:` from `.steering/tech.md` under `ROOT`, with the same expressions `check-document-set.py` uses. It finds the Rules table in `<docs>/CONTRACT.md` by a header row with `id` and `Tier` columns, matched without regard to case. It collects every row whose Tier, with `*` and backticks stripped, is `Judgment`. Then it checks each `<candidate>/<reviewer>/rules/*.md` that exists across `CANDIDATE_DIRS`, each directory on its own, because a dual-target project holds two copies and either can be the reference. A rule counts as defined only by a line matching `^\s*(?:#{1,6}\s+|[-*]\s+\*\*)<id>(?![\w-])`. That covers both shipped shapes, `## PY-001 —` and `- **G-1 —`, and matching on a mention instead would let the stripped path pass on a rulebook that says "unlike G-3". The errors go into the existing `errors` list, ahead of the no-locks early exit, so a project with no locks is still checked. A remote `- Docs:` prints a line saying the contract was not checked. It does not fail: failing would leave every multi-repo project unable to keep this guard, and `check-document-set.py` can be left off the Validators line in that case while this guard cannot. **The prose:** step 1's table gains the row, and step 3's reviewer bullet gains the upgrade branch (AC2) and the stripped branch (AC3). That second branch tells `init` that the guard fails until the ids are carried, so step 4's green tree comes from `contract`, not from editing the contract. Narrower — prose only — leaves the next disagreement silent, whatever creates it: `contract`, a hand edit or a re-run. Wider — a check on severities and wording as well — has to parse rule text in a form the rulebooks do not share.
- Affected files: `assets/check-locks.py`, `scripts/test-gates.sh`, `skills/init/SKILL.md`, `scripts/check-skill-contracts.py`, `docs/CONTRACT.md`, `.steering/tech.md`, `AGENTS.md` (and `rules/AGENTS.md` through its symlink), `docs/BACKLOG.md` row 1, `.specs/84-init-keeps-the-project-rulebook/observations.md`.
- **Blast radius:** `check-locks.py` runs on this repository's `- Validators:` line, and its contract half is green here (18 of 18 Judgment ids are defined in `.claude/agents/gate-sdd-reviewer/rules/`, probed while drafting). The `test-gates.sh` lock fixtures (cases 15–19) have no `.steering/` and no contract, so they keep their current outcomes. Consumers get the new half only when `init` copies the file again. A consumer whose contract really does cite ids its rulebook lacks then goes red, and that red is the defect this issue describes, now reported. A contract still carrying the template's `<PFX-001>` placeholder as a Judgment row is reported too, because it cites a rule nobody wrote. The CI `lint` job holds `assets/check-locks.py` to `ruff` and `shellcheck` under its pins, so the new code must be clean under them (#81). It stays stdlib-only and runs under Python 3.9, as it did before (`from __future__ import annotations` keeps the new `| None` annotations unevaluated). `docs/CONTRACT.md`'s own table must keep parsing: the probe read it with the column positions this design assumes.
- Why this cannot recur: the contract and the installed rulebook can no longer disagree on an id without the validator line and CI going red, whichever path produced the disagreement. Each branch has a case that fails before the change. The `init` sentences that keep a project rulebook are pinned, so trimming them fails `check-skill-contracts.py`.
- Version: minor, 0.29.0 → 0.30.0 — a shipped guard gains a failure mode and `init`'s flow gains two branches. It is a step of `implement` after the receipt, not a task.
