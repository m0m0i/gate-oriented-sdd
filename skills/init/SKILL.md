# init — Install the harness into a project

Runs **inside** the target project. It interviews the repository first and the user second, because most of what varies is discoverable and asking about it wastes the one resource the user actually spends: attention.

Migration is the common case. **Treat a greenfield repo as the special case, not the default.**

## Step 1 — Detect, don't ask

Read before asking anything:

| Signal | Tells you |
| :-- | :-- |
| lockfiles, `package.json`, `pyproject.toml`, `pubspec.yaml`, `go.mod`, `Cargo.toml`, `Gemfile` | language and package manager |
| scripts/tasks in those files, CI workflow files | the real validator commands — the ones that already pass |
| existing test directories and naming | the test runner and where tests live |
| `git log --format=%s -50` | the commit convention actually in use, not the one in CONTRIBUTING |
| `.github/ISSUE_TEMPLATE/`, existing labels | the issue taxonomy already in use — adopt it rather than imposing one |
| `git remote -v`, existing PR templates | the tracker and default branch |
| existing `.claude/`, `.agents/`, `CLAUDE.md`, `GEMINI.md`, `AGENTS.md`, `.specs/` | what is already installed, which harness is active, and what you must not overwrite |
| a reviewer in `.claude/agents/` or `.agents/agents/` — the one `- Reviewer:` names, or any `<name>.md` with a `<name>/rules/` beside it — its `rules-lock.json`, and `<docs>/CONTRACT.md` | the rules this project compiled for itself, which step 3 keeps rather than replaces, and the Judgment ids its contract cites, which the installed rulebook must define |

**Detect the target harness before asking.** Check filesystem markers (`.claude/` or `CLAUDE.md` indicates Claude Code; `.agents/` or `GEMINI.md` indicates Antigravity; both indicates dual-target) and runtime environment signals (environment variables like `CLAUDE_CODE`, `ANTIGRAVITY`, or agent tool availability). If signals are unambiguous, proceed with the detected target harness(es) without asking.

**Run each candidate validator before adopting it.** A command copied from a README that fails on a clean checkout will make the quality gate block every turn from day one, and the user will disable the gate rather than debug it. If a validator fails on a clean tree, say so and ask whether to fix it, omit it, or record it as known-failing.

## Step 2 — Ask only what is left

If target harness signals are ambiguous or neither is detected, confirm target harness(es):
`Which harness(es) should this project configure? [1] Claude Code, [2] Antigravity, [3] Both`

At most five questions, highest consequence first, each with a recommended answer:

1. **What quality property does this project own?** Correctness, latency, safety, accessibility, cost — the one a defect would most damage. This anchors every severity in the reviewer, so it is the question worth spending the most on. There is no good default; ask.
2. **Is there a source of truth above this repo** — a design hub, an ADR set, a shared contract — and how are its documents referenced?
3. **Which validators are gating** (block a turn) versus advisory (report only)?
4. **Confirm the detected commit convention and branch naming.**
5. **Anything the reviewer must never flag** — a deliberate deviation it would otherwise read as a violation.

## Step 3 — Write

**Install the harness and record which document set this project signed up for. `init` writes neither set.** The five documents are authored by the skills that own them, each of which interviews for content `init` does not have; a placeholder written here would be the `TODO` this step's closing rule forbids, one directory over. What `init` owes is the harness those skills run inside, the three issue templates, and an honest statement of where the project stands. Count the two in their own units and they do not collide. **Ten of the thirteen skills** are in a minimum install — `init`, `prd`, `design-doc`, `backlog`, `sprint`, `spec`, `clarify`, `implement`, `worklog`, `archive` — and between them they produce **five documents** (`PRD`, design doc, backlog, spec, work log) and **three issue templates**. Five of those ten produce no document at all, which is why counting documents never finds them: `init` installs the harness, `sprint` produces issues, `clarify` a section inside a spec, `implement` code and a receipt, `archive` a `git mv` and a `Status` flip. The remaining three are opt-in, each for its own reason — `northstar`, because step 2's interview already produces the `- Owns:` anchor by another route; `roadmap`, because nothing consumes what it commits to mechanically: under `full`, `check-document-cascade.py` asks only that it is reconciled against the PRD (#166); `contract`, because running it before there are commits and review findings to compile produces a *worse* rulebook rather than an absent one. Creating every document a large project would want, in a project that needed five, is how a harness gets abandoned in week two, so name the opt-in three and let the user choose rather than creating them by default. **Record the choice**: write `- Mode: bootstrap`, `- Mode: minimum` or `- Mode: full` on one physical line in `.steering/tech.md`. **A fresh install is `bootstrap`** — the harness is in place, the inception documents are not written yet — and that is the honest value at the end of this step rather than a lesser one, because the other two claim documents that do not exist and `check-document-set.py` checks the claim. `bootstrap` expires at the first spec the declaration did not name: on a fresh install, once `.specs/` holds one, the checker fails until the documents are written and the mode is declared. Say that to the user in the same breath as the mode, so the block, when it comes, is one they were told about. **A project with no `- Mode:` line is a fresh install only when it has no spec yet** — look in `.specs/` and `.specs/_archive/` for a directory holding `spec.md`, and under `- Docs:` for `PRD.md`, `DESIGN.md` and `BACKLOG.md`. Every project installed before the line existed is in that state, and `bootstrap` alone fails on it at once, because its specs already expired the window (#309). With all three documents present, it is an upgrade to `minimum` or `full`, by the Rules below. With specs and the documents not all written, it is **adopted**: first make sure the document checks that run are the plugin's, not copies from before 0.40.0, which cannot read the line this writes and would fail on it in step 4: on either harness, migrate the guards as the bullet after the hooks says, and on Antigravity refresh `.agents/hooks/`. Then write `- Mode: bootstrap` with `- Specs before bootstrap:` naming every one of those spec directories, comma-separated, on one physical line — the document-set check, run by the digest's `Harness checks:` command on the tree before the line exists, prints it written out. The documents are still owed: the next spec the line does not name ends the window, as the first spec ends a fresh install's, so say that too. The line is never extended afterwards; a project that needs another spec writes the documents. **Then ask which document set the project is signing up for and record the answer as `- Target: minimum` or `- Target: full`.** `- Mode:` cannot carry that answer, because it records what is true now and what is true on a fresh install is `bootstrap` — so without a target the first block names the three documents every project owes, which is the wrong list for an operator who chose six, and they discover what they signed up for at the moment it stops them. The target settles nothing and decides nothing: `check-document-set.py` still builds what it requires from `- Mode:` alone, and the target only changes which documents the messages name — both the advisory line before the first spec and the block at it. Ask it here rather than in step 2 because step 2 is capped at five questions and this is not one of the five: the choice is already in this step, in the opt-in three named above, and all that was missing is recording it. **Ask this only where the project carried no `- Mode:` line when this step began** — not where none exists now, because by this point a `- Mode:` line exists in every case — this step has just written one on a fresh install or an adopted project, and an upgrade carried one in — so a condition read after that is false exactly where the ask is wanted. A project that already carried one is an upgrade, and the Rules below say an upgrade changes nothing else — including a project still at `bootstrap`, which carries the line and may already have a `- Target:` the ask would overwrite without the diff those Rules require. **Omit the line if the user has no view yet.** Absent is a supported state: the messages then name the three documents every project owes and offer both sets to declare, which is exactly today's behaviour, and a target written to have written one is a claim nobody made. It is declared rather than worked out later from which files happen to exist, because that derivation cannot tell a deliberate omission from an abandoned install — and that distinction is the only reason the line exists. What that choice governs is which documents are created and which skills are in the flow — never whether a skill can be run. Every skill ships with the plugin and is always available.

- **`.steering/product.md`** — what this project is, who uses it, what it deliberately is not, and a `- Owns: <quality property>` line the reviewer and the digest both read.
- **`.steering/tech.md`** — the stack, and the exact commands, with these machine-read lines:
  ```
  - Validators: <the gating commands, comma-separated>
  - Reviewer: <reviewer name>
  - Source globs: <git pathspecs for reviewable source, space separated, e.g. :(glob)**/*.ts :(glob)**/*.py>
  - Docs: <where inception documents live — `docs/` by default, or the path/URL of a shared documentation repo in a multi-repo product>
  - Mode: <bootstrap|minimum|full — which document set this project signed up for, or bootstrap until it has one>
  - Target: <minimum|full — the set the operator chose, read only while Mode is bootstrap; omit it if they have not chosen>
  - Specs before bootstrap: <the spec directories a project adopted with specs already had, comma-separated, read only while Mode is bootstrap; omit it on a project with no spec yet>
  - Validator budget: <whole seconds the quality gate gives the validators before it blocks, 1 to 590; omit it unless they need more than the default 170; step 4 measures the suite and writes it when they do>
  ```
  The gates parse these, so a project changes its enforcement by editing steering rather than by editing hooks. Two consequences worth stating, because both fail silently:

  - **Each value must stay on one physical line.** The gates read them with `sed ... | head -1`, so a wrapped value is truncated at the first newline and the rest is lost without complaint.
  - **`Source globs` is a git pathspec, and `:(glob)` earns its place.** The value is interpolated unquoted so that each glob reaches git as its own pathspec, and the gates disable pathname expansion across that split (#1, #254), so a bare `*.py` reaches git as written rather than being matched against the repository root by the shell. `:(glob)` is still the form to write: a plain pathspec's `*` matches `/` as well, so a bare glob is wider than it reads, where `:(glob)**/*.py` says exactly what it means.
- **`.steering/structure.md`** — where code belongs, and where tests mirror it.
- **The harness checks** — `check-steering-anchors.sh`, `check-locks.py`, `check-document-set.py` and `check-document-cascade.py`, the guards that check the harness's own files. **On Claude Code, copy none of them into the project and put none on the `- Validators:` line.** The quality gate runs them itself, from the plugin's own tree through `hooks/harness-checks.sh`, before the line's commands, so a fix to any of them reaches the project by plugin update and the line holds only the project's own commands (#340). On Antigravity the hooks bullet below copies them into `.agents/hooks/` with the gates. By hand, beside the line, the session's digest names the command that runs them, on its `Harness checks:` line. What each one checks:
  - **The anchors.** The machine-read lines above are read with exact expressions, and a value written in a form the reader cannot see produces nothing and no complaint: the file looks right, the gate runs on a default, and nobody finds out. This harness lost its own quality anchor that way for a week by writing `- **Owns: ...**` instead of `- Owns: ...`. It also asks whether `- Validator budget:` can be honoured, with the quality gate's own readers: it fails a value the gate rejects, and a value above the shortest `timeout` a project hook file — `.claude/settings.json`, `.claude/settings.local.json` or `.agents/hooks.json` — gives the quality gate, less the 10 s the gate keeps back, which the gate would otherwise lower without a word. It fails a hook file the gates would block on, too: one that cannot be read or parsed, or that runs a gate with no `timeout` or with one of 10 s or less.
  - **The document set.** It verifies the filesystem against `- Mode:`, and it is the only route by which the mode reaches a gate: it runs as a check the gate runs, never as logic inside the gate, so the gate never branches on mode. A gate that branched on mode would be a switch that turns enforcement down.
  - **The document cascade.** It enforces that downstream documents carry `- Reconciled against PRD: <sha>` matching the latest commit touching `<docs>/PRD.md`. In `bootstrap` mode it defers with exit 0.
  - **The locks.** The reviewer bullet below.

  **Run them in the project's CI as well**, beside its other validators: the turn-end gate runs only when the source matching `- Source globs:` has changed since it last passed, and a document is never source, so CI is where the two document checks bite. On Claude Code that is `sh .gate-sdd/hooks/harness-checks.sh`, with the plugin checkout the unreviewed-work bullet describes; on Antigravity, `sh .agents/hooks/harness-checks.sh`. When `- Docs:` names another repository the runner reports the two document checks as not applicable, says so, and runs the other two.
- **`.specs/README.md`**, **`.specs/_archive/README.md`**, **`.work_logs/README.md`** — each stating its contract. Copy them from the plugin's `assets/directory-contracts/`, where each sits at its destination path with the leading dot dropped: `specs/README.md`, `specs/_archive/README.md`, `work_logs/README.md`. Copy rather than write: they state what the skills already assume — the status lifecycle and what the review gate reads in `.specs/`, the sweep that fills `_archive/`, append-only in `.work_logs/` — and a contract each install words for itself is one no two projects share. One that already exists is the project's, and the Rules below cover it.
- **`.github/ISSUE_TEMPLATE/`** — **absorb what is there, then copy what is left.** Copying first is what reopens this: the plugin's `bug.md` lands, the project's `bug_report.md` becomes the second template for a type that now has one, and the rename below has an occupied destination. The issue is the entry point to the whole flow: `backlog` creates typed issues, `spec` reads the type to choose its shape, and one issue becomes one spec, one branch, one PR. Leaving the entry point undefined leaves a hole in the middle of the process. `config.yml` sets `blank_issues_enabled: false` on purpose — an untyped issue makes `spec` guess, and it guesses feature, which is the wrong shape for a bug and for a chore. If the project has a reason to allow blank issues, say so and change it deliberately. **Absorb rather than duplicate**, and do it first: for each of the three types the project already has a template for, `git mv` each existing template to the canonical filename for its type — `bug_report.md` becomes `bug.md`, and one already at its canonical name is left alone, since `git mv` onto itself is a fatal error and a re-run is the upgrade path — keeping its body, its front matter and its labels exactly as they are (`mv` if it is not yet tracked; `git mv` is for the history, and it exits rather than degrading on an untracked file). **Then** copy whichever of `feature.md`, `bug.md` and `chore.md` is still absent after the renames, from the plugin's `assets/issue-templates/`, adapting *their* labels to the ones this project already uses — the absorbed ones keep theirs. Add `config.yml` only if the project has none: an existing one is theirs and may carry `contact_links:`, and the Rules line below covers it, so show the diff before changing `blank_issues_enabled`. Leave templates of any other type — `question.md`, `security.md` — exactly where they are: the checker does not look at them, and this is the one bullet that moves a file the project owns. If a type somehow has two, absorb one and leave the other alone rather than guessing which the team meant. Show the renames as a diff and get agreement first, as with any file the project owns. An existing template encodes decisions the team already made, and none of them is the filename: the canonical name is what the document-set checker verifies and what `spec` reads a type from, so those have to be the same file. **Never add a second template for a type the project already has** — the picker would then offer two, and the spec author would have to guess which one the reporter meant.
- **The unreviewed-work check** — run `check-unreviewed-work.sh` in the project's CI, on pull requests, from the plugin checkout below on Claude Code and from `.agents/hooks/` on Antigravity, where the hooks bullet copies it; on Claude Code nothing is copied into the project for it. Pass the event's head branch, head commit and base commit: on GitHub Actions that is `sh .gate-sdd/assets/check-unreviewed-work.sh "${{ github.event.pull_request.head.ref }}" "${{ github.event.pull_request.head.sha }}" "${{ github.event.pull_request.base.sha }}"`, with a full-history checkout (`fetch-depth: 0`) so the reviewed commit is present to diff against. The check reads the specs the head adds against that base as well as the one named for its branch, so a branch named any other way is still checked. Without the third argument it measures against the default branch, and fails when it can find none. **Deliberately not on the `- Validators:` line** — `review-gate.sh` already asks this question on turn end, in a message written for the person whose turn it is, and a second differently worded block in the same place buys nothing. What CI adds is the property the hook cannot have: a hook can be switched off and HEAD can be moved, and a pull request can do neither. That is #26, where the one enforced rule in this harness turned out to be one `git checkout` from silent. **Skip it only if the project has no CI at all** — and say plainly, then, that the review gate is a local signal rather than a guarantee. **On Claude Code the project has no copy of the checks or of `gate-lib.sh`**, so the workflow checks the plugin out and says where it is: a second `actions/checkout` step with `repository: m0m0i/gate-oriented-sdd`, `ref: main` or a release tag, and `path: .gate-sdd`, and `GATE_SDD_HOOKS: .gate-sdd/hooks` in the job's `env`, so that every check the job runs sees it. With `ref: main` a check fix reaches the job with the next run; a release tag runs that tag's checks until the workflow moves it. The checkout lands inside the workspace, so add `.gate-sdd/` to the project's `.gitignore`, which ruff and most linters and formatters honour, and exclude it explicitly from any tool in the job that walks the whole tree without honouring `.gitignore`; otherwise the project's own lint step fails on the plugin's files. At turn end the gate runs the checks from its own directory and needs no variable. In the session's own shell — where `implement` and the reviewer run them — the digest's command reads `GATE_SDD_PLUGIN_ROOT`, which the plugin's `SessionStart` hook sets, and names the remedy when it is unset. A terminal outside a Claude Code session runs `sh "${GATE_SDD_HOOKS:?set it to the hooks/ of a plugin checkout}/harness-checks.sh"`, with `GATE_SDD_HOOKS` set by hand to a plugin checkout's `hooks/`.
- **The reviewer** — read the end of this bullet first if the agents directory already holds one, or `<docs>/CONTRACT.md` cites Judgment rules. Otherwise, from the closest reference implementation (`ts-reviewer`, `python-reviewer`, `dart-flutter-reviewer`), or from `_template/` for an unrecognised stack. **The sources are in the plugin's `reviewers/` directory**, which has the shape of the directory you are installing into: copy `reviewers/<name>.md` and the `reviewers/<name>/` directory beside it (its `rules/` and `rules-lock.json`) into the project's agents directory. The plugin registers none of them as an agent, so the copy in the project is the only reviewer a session can invoke. Copy the contract to `_shared/reviewer-contract.md` **inside the agents directory you are installing into** — `.claude/agents/_shared/reviewer-contract.md` for Claude Code, `.agents/agents/_shared/reviewer-contract.md` for Antigravity. The reviewer names the relative form — which says where the file lives — **and** the concrete path for each harness, which is what it can actually open: a reviewer reads its own instruction with the project root as its working directory, so the relative form alone resolves to nothing. **Keep the concrete path for the harness this project uses; never leave only the relative form.** Trimming the other is optional, and leaving both is harmless. `check-locks.py` is a harness check, so on Claude Code nothing is copied for it: re-pin the rulebook after any edit with `python3 "${GATE_SDD_PLUGIN_ROOT:?is unset; start a new Claude Code session}/assets/check-locks.py" --update` in the session's shell, run from the project — on Antigravity, `python3 .agents/hooks/check-locks.py --update` — and its drift message names the same commands. It verifies the repository it is run in, whichever copy runs it. **A reviewer already in the agents directory is the project's, not a reference to replace.** Keep it, its `rules/` and its `rules-lock.json` exactly as they are, and copy no reference reviewer or rulebook over them: its rules are the ones `contract` compiled and `<docs>/CONTRACT.md` cites, and a reference rulebook defines none of them. Bring only the file the plugin owns beside it, `_shared/reviewer-contract.md`, up to the plugin's, through `upgrade-install.py` as the hooks bullet runs it — on Claude Code, `python3 "${GATE_SDD_PLUGIN_ROOT:?is unset; start a new Claude Code session}/assets/upgrade-install.py" --project .` — which replaces a text this plugin shipped and shows the project's own edit to it as a diff to ask about (#343). Then run the harness checks to verify the rulebook against its lock. Re-pin with `--update` only a drift the user confirms was deliberate: `init` edited nothing in the rulebook, so re-pinning it here could only accept a change nobody chose. Where the rulebook has no `rules-lock.json`, say so: `--update` cannot create one (#19), so the rulebook stays unpinned. **Where the reviewer is gone and `<docs>/CONTRACT.md` still has Judgment rows — the stripped path — look in history before installing anything.** Restore the reviewer and nothing else beside it — `<agents dir>/<reviewer>.md` and `<agents dir>/<reviewer>/`, where `<reviewer>` is the name `- Reviewer:` gives or, with steering gone too, the one `git log --diff-filter=D --name-only -- .claude/agents/ .agents/agents/` shows. Deleted in the working tree but present in `HEAD`, it comes back with `git checkout HEAD -- <agents dir>/<reviewer>.md <agents dir>/<reviewer>/`. Removed by a commit, `git log --diff-filter=D --format=%H -1 -- <agents dir>/<reviewer>/` names that commit, and `git checkout <that commit>^ -- <agents dir>/<reviewer>.md <agents dir>/<reviewer>/` restores it as it was. Offer that, show what it restores, then continue as for a reviewer already in the agents directory, above: that branch is what brings `_shared/reviewer-contract.md` up to the plugin's, which the restore leaves as it was. Only when history holds none, install the reference reviewer and say plainly that every Judgment row whose id it does not define now has no enforcer: `check-locks.py` names each one and fails until they are defined. Run `contract` to compile them into the installed rulebook before step 4 arms the gate, rather than editing the contract to match the reference.
- **The hooks** — the two harnesses get them differently, and the difference is where the gate runs from.
  - On **Antigravity**, the plugin's `assets/upgrade-install.py` makes the install and keeps it: it copies the set its table, `assets/shipped-texts.json`, names under `copy_set` — the gates and `harness-checks.sh` from `hooks/`, the four harness checks and `check-unreviewed-work.sh` from `assets/`, flat in `.agents/hooks/` — and renders `hooks/templates/antigravity.hooks.json` into `.agents/hooks.json`, in the parsed structure, so a fast check holding `&` or a quote arrives escaped (#343). Run it as `python3 <plugin>/assets/upgrade-install.py --project <project root>`, where `<plugin>` is the plugin directory you are installing from. On a fresh install, run it with `--install --fast-check '<the per-edit check>' --write`. **On a re-run, run `upgrade-install.py` before copying anything**, and copy nothing by hand. It reports each file as `current`, `shipped` (an earlier text of this plugin, which it replaces), `missing` (which it adds) or `edited` (the project's own edit, shown as a diff), and the hooks file as current or as a proposal naming the template that wrote it, keeping the fast check, a matcher and the fast-check group's `enabled` the project chose, and every entry of its own. Ask the user its questions one at a time, then run it again with `--write` and the answers: `--replace <path>` for each edited file the user agrees to replace, `--hooks-json` to accept the hooks file's proposal, and `--fast-check` or `--fast-check-enabled` where it asks for one. It writes the copies only when the hooks file will be current after the run, checks that every file can be written before it writes any, writes the hooks file last, and names every file it wrote; a write that still fails part way exits 1 and names what it had already written. Under Antigravity's terminal sandbox the first write can be refused — `Operation not permitted`, and `Already written: nothing` — because the sandbox refused the temporary file the script creates in `.agents/hooks/` on CLI 1.4.12; run the same command again with the bypass the CLI offers, which the headless sessions of those runs granted; how an interactive session asks for it has not been observed (`docs/verified.md`, #343). It also reports each pre-0.41.0 guard in `scripts/` as a question until the guard migration below removes it. After it writes, run the harness checks, as step 4 says, and report what they fail: an install older than a check fails it from the first turn the new gate runs. Exit 0 is nothing to upgrade, or all applied; 3 is changes or questions still pending; 4 is no install; 1 is a refusal — stop, say what it refused, and never fall through to a fresh copy. To see which of several projects are behind after a plugin update, give it one `--project` each, without `--write`. The quality gate runs `harness-checks.sh` from its own directory, and the anchor check fails a `.agents/hooks/quality-gate.sh` with no runner beside it. Only `{{FAST_CHECK}}` and `{{HOOKS_DIR}}` are substituted; the blocking quality gate ships as a script and reads the `- Validators:` line, so do not inline the validator commands into the hooks file. A plugin-shipped hook runs there with the plugin directory as cwd, which is why the copy exists (`hooks/templates/README.md`), and a gate or check fix reaches the project by running `init` again. The rendered `Stop` timeouts, 600 for the quality gate and 120 for the review gate, are each gate's ceiling, not its budget: each gate blocks at a deadline of its own, never later than 10 s before the shortest `timeout` it can see, because Antigravity kills a hook at its `timeout` and ends the turn as a pass. Leave them as rendered. The quality gate's budget lives in steering, in `- Validator budget:`, and a lower `timeout` only lowers it: a `hooks.json` rendered earlier at 180 and 30 holds the gates to 170 s and 20 s until `init` renders it again, so refresh the hooks file with the gates, never the gates alone. The file holds two named groups, each with its own `enabled`: `gate-sdd` runs the digest and both gates, and `gate-sdd-fast-check` runs the fast check, so a project that wants the fast check off sets `enabled` false on that group only — false on `gate-sdd` stops both gates, and the anchor check fails it (#330). Each `Stop` command runs its gate as `GATE_SDD_HARNESS=antigravity sh …`: that marker is how the gate knows Antigravity reads its block, whatever variables a session nested in another harness inherited, so keep it if you change the command (#302). The fast check is rendered inside `( … ) 1>&2; echo '{}'`, because Antigravity reads a hook's stdout as its JSON result and a linter's own output there is a parse error after every edit (#324); keep that envelope if you change the check. When the stack has no per-edit check, render `{{FAST_CHECK}}` as `true`, never empty: an empty one is a shell syntax error in both templates' envelopes.
  - On **Claude Code, copy no gate script.** Since 0.23.0 the gates run from the plugin: its `.claude-plugin/hooks.json` runs `quality-gate.sh` and `review-gate.sh` on `Stop` and `steering-digest.sh` on `SessionStart`, with the project as cwd, silent in a project without `.steering/`, so a gate fix reaches the project by plugin update with no pull request in it. Render `hooks/templates/claude-code.settings.json` into `.claude/settings.json` instead. It declares the marketplace with `"autoUpdate": true` and no `#ref` — a project-scope pin under a marketplace name the user's own settings already know is ignored, `docs/verified.md` — enables the plugin, sets `FORCE_AUTOUPDATE_PLUGINS=1` in `env`, and carries the per-language `PostToolUse` fast check, which really is per-project. The `env` line keeps the auto-update pass on in a session the Claude desktop app starts: the app sets `DISABLE_AUTOUPDATER=1`, which turns the pass off, so without the line a machine used only through the app stays at the version it installed and no gate fix reaches it (#274, `docs/verified.md`). A collaborator turns it off for themselves with the same key set to `"0"` in their `.claude/settings.local.json`. Say to the user that the declaration puts the harness in front of everyone who opens the repository, and that `claude plugin install gate-sdd@gate-oriented-sdd --scope project` is no substitute for it: that command writes only the `enabledPlugins` entry, with neither the marketplace nor `autoUpdate` (`docs/verified.md`, #257). **Migrating a Claude Code project installed before 0.23.0 takes four steps, and the first alone leaves it broken:**
    1. Delete `gate-lib.sh`, `quality-gate.sh`, `review-gate.sh` and `steering-digest.sh` from `.claude/hooks/` and the `Stop` and `SessionStart` entries from `.claude/settings.json`, keep its `PostToolUse` entry, and add the declaration with its `env` line. While those entries remain, the plugin's gates stand down and the project keeps running its stale copies. That holds only for an entry that names its copy by a relative or absolute path, or through `$CLAUDE_PROJECT_DIR`, with the copy on disk. An entry that reaches the copy any other way, through another variable or a script of its own, does not stand them down. Both sets then run, two blocks for one failure, until this step removes the entry. The copied files alone, with no entry, do not stand them down either.
    2. Migrate the guards, as the next bullet says. A copy from before 0.23.0 looks for `gate-lib.sh` only in the directories step 1 just emptied, so a copy left on the line blocks every turn that changes source and fails CI (#263); the migration takes it off. Bring `_shared/reviewer-contract.md` up to the plugin's through `upgrade-install.py`, as the reviewer bullet says; never the reviewer itself, which the project adapted.
    3. Give every CI job that runs a harness check or the unreviewed-work check — a job that runs the `- Validators:` line included — the plugin checkout, `GATE_SDD_HOOKS` and the `.gitignore` entry the unreviewed-work bullet above describes.
    4. Search the project for anything else that read what step 1 deleted: `.claude/hooks/` and the four filenames in CI workflows, test fixtures and scripts, and context files — `AGENTS.md`, `CLAUDE.md`, a README — that say the gates run from `.claude/hooks/` or that enforcement does not depend on the plugin, which a session reads as instructions. None of these is a file `init` wrote, so show each change as a diff and get agreement first, as the Rules require.

    On a dual-target project do step 1 for `.claude/` only: the Antigravity half keeps its copies in `.agents/hooks/`, refreshed with the runner and the checks, and must not be told to delete them. The plugin's runner reads its own tree whatever `.agents/hooks/` holds, and the anchor check fails an `.agents/hooks/quality-gate.sh` with no runner beside it. Then **Step 4 — Prove it works** below proves the migration.

    Every machine that opens the migrated project needs the plugin at 0.23.0 or later. No version before 0.23.0 ships a Claude Code hook, so on an older install a migrated project runs no `Stop` gate at all, and nothing says so, until the plugin updates there: with the `env` line, the pass in that machine's first desktop session in the project updates the plugin and the gates load at its second; without it, a by-hand update. `claude plugin list` shows each machine's version (#274).
- **Migrating the guards (#340), on either harness: a project with harness checks in `scripts/`.** Before 0.41.0 `init` copied `check-steering-anchors.sh`, `check-locks.py`, `check-document-set.py`, `check-document-cascade.py` and `check-unreviewed-work.sh` into the project's `scripts/` and named all but the last on the `- Validators:` line, so a plugin update reached the gate and never the copies. Now the gate runs them from its own tree. Migrate in this order, showing each change as a diff first, as the Rules require:
  1. **Make sure every project-side gate copy carries a runner before any entry leaves the line.** On Antigravity, refresh the `.agents/hooks/` set as the hooks bullet says. On Claude Code, the pre-0.23.0 migration above deletes any `.claude/hooks/` copy, and no gate is ever written there.
  2. **Remove the copies in `scripts/`.** `upgrade-install.py` reports each as a guard with its class: remove one it calls `shipped` or `current`; ask first about one it calls `edited`, and about a symlink, naming its target: a project may have edited one, and its edit is the project's to keep or drop.
  3. **Drop each `- Validators:` entry that names a harness check** — none while the report says a kept quality gate does not run `harness-checks.sh`, since the line is then the only place the checks run — matched by its last path component, whatever `./`, `sh`, `python3` or directory comes before it, and list any entry that names one of these files in a form that cannot be matched.
  4. **Point CI at the plugin checkout**, as the harness-checks and unreviewed-work bullets above say.
  5. **Propose the runner to every project reviewer whose allow-list names the validators**, whether it copies the line or names it: its Bash policy gains "the harness checks, by the command the session's digest names".
  6. **Search the project for anything else that names a copy:** CI workflows, context files — `AGENTS.md`, `CLAUDE.md`, a README — and its contract's command list and re-pin step. None of these is a file `init` wrote, so propose each change as a diff.

  Until a project migrates, its old entries run beside the gate's checks. A stale copy can only add a block, never remove one, and the digest says so. A fresh install copies none of them.
- **`AGENTS.md`**, always canonical. Point to it with CLAUDE.md for Claude Code, GEMINI.md for Antigravity, or both for a dual-target project. **On Claude Code, `CLAUDE.md` imports it with a line reading `@AGENTS.md`**, not a sentence telling the agent to read it. Under Claude Code's default **Project instructions** setting, a `CLAUDE.md` turns off native `AGENTS.md` reading, and a prose pointer loads the file only if the model decides to open it, so a session starts without the project's canonical context and nothing says so (#239, `docs/verified.md`). The import works under every setting except `managed-only`. Where the project already has a `CLAUDE.md`, add the line to it and show the diff first; leave the rest of the file as it is. **On Antigravity, `GEMINI.md` is a symlink to `AGENTS.md`** (`ln -s AGENTS.md GEMINI.md`): Antigravity expands no `@AGENTS.md` import, follows no prose pointer, and reads no project `AGENTS.md` on its own, while a symlinked `GEMINI.md` loads (#239, `docs/verified.md`). Where the project already has a `GEMINI.md` of its own, show the diff of moving its content into `AGENTS.md` and get agreement before the symlink replaces it; replacing it without that discards the project's rules.

**Populate every file. Never leave a `TODO` in a steering file.** An unpopulated steering file is worse than none: it teaches the agent that steering files are noise, and that lesson generalises to the ones you did fill in.

## Step 4 — Prove it works before declaring success

Do not report completion on files written. Verify:

1. Every gating validator runs clean on the current tree, run by hand in the session's own shell — where `implement` and the reviewer will run them. **Time that by-hand run, and size the quality gate's budget from it, before the gate first runs.** Read `date +%s` before and after the whole `- Validators:` line, in that same shell, and report the whole seconds to the user whatever they are. The rule: at 85 s or less write no `- Validator budget:` line, over 85 s write twice the measured time and never more than 590, and where the line already exists propose only a raise, as a diff, never lowering a value someone chose. Say why whenever you write or raise it. When twice the time is over 590, write 590 and say plainly that the suite may still be cut off; the remedies are the ones the gate's own block names, a faster suite or the slow validator moved off the `- Validators:` line to CI. The value also stays at or below the shortest `"timeout"` a project hook file gives the quality gate, less the 10 s the gate keeps back. That is normally the 590 maximum: Claude Code's rendered settings carry no quality-gate entry, so the gate falls back to its 600 s ceiling, and on Antigravity step 3 renders 600. When a hook file the project keeps holds it lower, write that bound and name the file, because the anchor check fails a line above it; when that bound is below twice the time, give the same warning, with the gate's remedy for it: raise that `"timeout"` to 600, or re-run `init`, which renders it. Run the digest's `Harness checks:` command inside the same two reads, first, because the gate runs it first and counts it against the same budget. A line written or raised came after the run that checked it, so re-run the anchor check on the tree that holds it. Then the quality gate exits 0, run once on that tree: on Claude Code `sh "${GATE_SDD_PLUGIN_ROOT:?is unset; start a new Claude Code session}/hooks/plugin-gate.sh" quality-gate.sh` from the project root, on Antigravity `sh .agents/hooks/quality-gate.sh`. Timing comes first because a suite over the default 170 s would be blocked by that run before any line exists, and a first run that passes records a pass that a later run skips on, because the record does not hold the budget line. That by-hand run, and the pass it records, used this session's own `PATH`, which a hook need not have, and because the pass is recorded, the first turn end after an edit is the first run under the hook's `PATH`. For each validator whose first word, after any leading assignments, is a bare name with no `/` in it, compare `command -v <word>` in the session's shell with `env PATH=/usr/bin:/bin:/usr/sbin:/sbin sh -c 'command -v "$1"' sh <word>`, testing each for a non-zero status, and warn about every word that resolves only in the session's shell: a tool a version manager keeps under `$HOME`, one in Homebrew's `/opt/homebrew/bin` or `/usr/local/bin`, or a name that is only an alias or a function of that shell. The warning blocks nothing and changes no `PATH`. It names the word and what a person can do, the remedies the gate's own block gives: on Claude Code, start `claude` from a terminal whose shell has the tool on its `PATH`, or, for the desktop app, put the tool's directory on the login shell's `PATH`, then quit and reopen the app; on Antigravity, start `agy` from such a terminal. On Claude Code the plugin's `SessionStart` hook sets `GATE_SDD_PLUGIN_ROOT`; if it is unset, the plugin was not enabled when this session started, so say so and have the user start a new session before going on, because a validator that passes only at turn end gives `implement` and every review a verdict the gate does not. Arm the gate on a green tree — otherwise the user's first turn is blocked by a failure that predates them, and their first act is to disable it.
2. The review gate, through the same command as step 1 with `review-gate.sh`, exits silently on the current branch — if it fires immediately, the scoping is wrong and the user's first experience of the harness is a false block.
3. Both gates actually block when they should: introduce a trivial lint violation, confirm the quality gate fires through the same command, revert it.
4. **The reviewer is spawnable.** You just wrote it into the project's agents directory, and a subagent registered mid-session is usually not available until the harness restarts. Check whether it can actually be invoked — if it cannot, **say so and tell the user to restart before their first `implement`.** This is not tidiness. `implement` step 2 falls back to running the reviewer's procedure inline when it is not spawnable, which means the author of the diff reviews their own work. That fallback exists for good reasons and it still finds real defects, but it is not the independence the judgment layer is sold on — and on a fresh install it is not the exception, it is guaranteed. A restart costs seconds; a project whose every early review was a self-review does not find that out until someone reads the receipts.
5. Report what you verified, and anything you could not. The report carries step 1's `PATH` warning, each word with its remedies, or says that the comparison found none.

## Rules

- **Never overwrite, rename or move an existing `.steering/`, `.specs/`, `.work_logs/`, `AGENTS.md` or `.github/ISSUE_TEMPLATE/` file without showing a diff and getting agreement.** Merge into what is there, or absorb it into the canonical name where step 3 says so — but never without the diff first. The verb matters as much as the list: `.github/ISSUE_TEMPLATE/` is here because step 3 now *renames* a file the project owns, and a rule that said only "overwrite" would not have reached it.
- The directory names `.specs/`, `.steering/`, and `.work_logs/` are fixed. They are not configurable, because every skill body references them literally, and that is precisely what lets one copy of a skill serve every project without templating.
- If the project already has a harness from an earlier version, upgrade it rather than reinstalling: an Antigravity install, and the reviewer contract on either harness, through `upgrade-install.py` as the hooks bullet says; on Claude Code otherwise through the migrations above.
- **A project that already carries a `- Mode:` line is an upgrade, never a fresh install.** Read the line first and offer to move it up, never down: `bootstrap` to `minimum` or `full` once the inception documents exist, `minimum` to `full` by running the three opt-in skills — and change nothing else. Re-running the scaffold over a project that already chose would recreate documents its author deliberately declined, which is the failure the mode was recorded to prevent.
- **A project with no `- Mode:` line, specs on disk and the inception documents not all written is an adoption** — neither a fresh install, which has no spec, nor an upgrade of a mode it never declared. Step 3 routes it, and the line it writes names only the specs already there.
- **Stop before adding configuration for its own sake.** If you find yourself designing a file that describes how to describe a language, the harness has drifted from its purpose: three concrete reviewers people copy beat one abstraction people configure.
