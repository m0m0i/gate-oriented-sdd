## 2026-10-21 — m0m0i (Claude Code), #331: a late pass no longer outlives a later failure

### Summary

The quality gate now orders overlapping runs in one worktree instead of trusting whichever finished last: a per-worktree token names the latest run to start or fail, and a pass counts only while the token names its writer. The spec was amended three times mid-implementation, each from a review, and the reviewer came back CLEAN. Version 0.35.0.

### Activities

- **331-a-late-pass-does-not-outlive-a-later-failure (#331)**: bug-shaped spec, one clarification (Q1: any failure ends every earlier-started pass), approved, then four tasks, each red then green, each reviewed by a read-only multi-lens workflow before its commit.
  - **T1** (`586bba2`): the token, the record's writer line, the skip's check at read time. Cases 340 (the reproduction) and 341 (stale writer); case 298's `mv` shim narrowed to the record.
  - **T2** (`caf0db7`): a failure is an ordering event, written by the child at every failed validator and by the parent's `qg_block` on every block. Cases 342–346, each red on T1's code; mutations show 343 pins the child's half and 345 the parent's.
  - **T3** (`677bf60`): writes only over nothing or a regular file, the failed step named, a token that cannot be written dropped, and a residual that cannot be dropped named at the start and in both halves' blocks. Cases 347–350; case 290's leftover check widened.
  - **T4** (`f34dee0`): `docs/DESIGN.md`'s Pass record row, `docs/layout.md`, the gate's header comment.
- **Spec amendments**, each in its own commit before the code it judges:
  - `9b5b74e`: a failure is written inside the validator loop and by the parent, because a run cut off after a failed validator never reached the post-loop write.
  - `814c640`: "mixed versions are safe" is true of the record's format, not the race.
  - `b0d1df7`: the write happens at every failed validator, not only the first. The T2 review reproduced a red tree skipped when a run started between two failures.
- **Reviewer** (`gate-sdd-reviewer`, subagent): CLEAN at `37a6a26`, 0 blockers, 0 high. The suite passes 363/0 under sh and dash.

### Decisions

- **Order the runs, do not lock them.** A lock would count its wait against #304's deadline and need stale-lock recovery, and a recovery that guesses wrong is either a false block or a fail-open.
- **The token's residual is named whenever it can be neither written nor removed**, not only when the record is stuck too, as Design step 3's wording had it. A later-started run still in flight can record after this run's removal. The reviewer agreed the code is right and the spec sentence is narrower than it. The spec wording was left as is and the divergence is recorded here and in the pull request.
- **Reviewer LOW accepted, not fixed**: the child's and the parent's "last pass record could not be removed" sentence also appears when the failure's token write succeeded, and then no skip can honour that record. Conservative, and it almost never fires on its own, because the token and the record share a directory and fail together (case 349). Fixing it after a CLEAN verdict would re-stale the receipt for a message-wording change.
- **Untested by design**: where the child writes (at each failure, or after the loop). The two differ only when the parent dies without building a block, for example under a SIGKILL of the whole group. Recorded on T2's line.
- **Minor bump, 0.35.0**: a gate behaviour fix, following #297 and #304.
